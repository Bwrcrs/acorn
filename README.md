# Acorn 橡果

一个从零手写的小数据库。C++17，不依赖任何第三方库。

> 橡果很小，但里面已经装着一整棵树的形状。

**当前进度：阶段 6 完成，115 项回归测试全过。**
`CREATE TABLE` / `INSERT` / `SELECT ... WHERE` / `UPDATE` / `DELETE` / `DROP TABLE` /
`CREATE INDEX` / `DROP INDEX` / `ORDER BY` / `LIMIT` / 聚合函数 / 算术表达式
/ `BEGIN` / `COMMIT` / `ROLLBACK` 都能跑，带 REPL、命令行、调试开关。
路线图上的六个阶段到这儿全部做完了。

数据**真的落在磁盘上了**：4KB 固定页、槽位页结构、64 格时钟页缓存、空闲页链表。
加 `-d 文件` 数据就活过进程退出；不加 `-d` 是内存库，跑完就没了。

**索引也真的能用了**：一棵自己写的 B+ 树，叶子节点串成链，键是
`(列的值, 行号)` 这个复合键。`WHERE id = 5`、`WHERE id > 100` 这类条件
不用再扫全表。查询计划器自己判断"这个条件能不能走索引"，**判断错的方向只有一个**：
认不出来就退回全表扫（答案还是对的，只是慢）。

**改了的东西现在能反悔了**：一份自己写的**回滚日志**（`<库文件>-journal`）。
`BEGIN` 之后要么 `COMMIT` 全部生效、要么 `ROLLBACK` 全部撤销；
**不敲 `BEGIN` 的话每条语句自己就是一个事务**——所以一条改到一半失败的
`UPDATE` 不会留下半条语句的痕迹。写到一半断电/被 kill 也一样：
下次打开时照日志退回去，回到事务开始前那一刻。

**好几个进程现在能一起用了**：一把操作系统给的**文件锁**，放在库文件旁边的
`<库文件>-lock` 里。读的可以一起读，写的独占，别人占着就当场报错（不会静静地
卡住），愿意等就加 `--lock-wait=毫秒`。**放锁是内核做的**——进程不管怎么没的，
锁立刻就没，所以没有需要人去清理的僵尸锁。

**顺带补掉一个真 bug**：库文件叫中文名的时候以前根本用不了（`-d 测试库.db`
报"目录不存在？"，而目录明明在）。原因见下面的「路径：一个字节都不该被猜」。

---

## 这是什么，为什么做它

刚做完 Nova（一个解释器）。Nova 的核心是"把一棵树走一遍，边走边算"——
求值、作用域、闭包，都是围绕着**树**打转。

数据库换个方向：核心不是树，是**数据怎么摆**。同一份数据，摆在内存的
`vector` 里是一种写法，摆在 4KB 的磁盘页里是另一种写法，摆在 B+ 树的叶子里
又是另一种。这是编译器那条线上完全碰不到的问题。

Acorn 的目标不是"做一个能用的数据库"（那用 SQLite 就行了），
而是把数据库**每一层都自己写一遍**，看清它是怎么搭起来的。

## 快速开始

```bat
build.bat               编译（默认带调试信息）
build.bat release       优化版
build.bat nopause       编完不暂停（给脚本用）

acorn.exe                                  进 REPL（内存库）
acorn.exe -d my.acorn                      进 REPL，数据存进 my.acorn
acorn.exe script.sql                       跑脚本
acorn.exe -d my.acorn script.sql           跑脚本，写进 my.acorn
acorn.exe -d my.acorn -e "SELECT * FROM users;"
acorn.exe --ast -e "SELECT * FROM t WHERE a = 1 AND b = 2;"
acorn.exe --tokens -e "SELECT * FROM t;"
acorn.exe -d my.acorn -e "BEGIN; INSERT INTO users VALUES (2, 'bob'); ROLLBACK;"
acorn.exe -d my.acorn --lock-wait=2000 -e "INSERT INTO users VALUES (3, 'carol');"
acorn.exe -d my.acorn --crash-at=commit -e "BEGIN; INSERT ...; COMMIT;"   <- 测试专用
acorn.exe -d my.acorn --hold=5000 -e "SELECT * FROM users;"               <- 测试专用
acorn.exe -d 中文名也能用.db -e "CREATE TABLE t (id INT);"                                <- 路径是 UTF-8
```

**`--lock-wait` 是"别人占着的时候愿意等多久"**，默认 0——也就是当场报错。
默认不等是刻意的：一个静静地卡住的程序比一个会报错的程序难查得多。

**加不加 `-d` 是两种完全不同的东西**：不加就是内存库（像 SQLite 的 `:memory:`），
进程一退全没；加了才是文件。下面这些命令连着敲，第三次还能看到前两次插的行：

```bat
acorn.exe -d my.acorn -e "CREATE TABLE users (id INT, name TEXT);"
acorn.exe -d my.acorn -e "INSERT INTO users VALUES (1, 'alice');"
acorn.exe -d my.acorn -e "SELECT * FROM users;"      <- 上一行的数据还在
acorn.exe -e "SELECT * FROM users;"                  <- 内存库，这里会报表不存在
```

REPL 里的元命令：

```
.help            帮助
.tables          列出所有表
.indexes         列出所有索引
.schema          列出所有表和索引的定义
.schema users    看某张表的结构（连着它身上的索引）
.info            库在哪个文件、几张表几个索引、页缓存用了几格、
                 这个进程现在拿着什么锁
                 （事务开着的话还会说"已记 N 页的旧内容"）
.quit / .q       退出
```

`CREATE INDEX` 之后查询不用改一个字，**结果也不会变**——只是快。
这件事有一整份测试在盯着（`index_big.disk` 里那两张一模一样的表 `d` 和 `d2`，
只给 `d` 建了索引，每条查询各跑一次，答案必须一个字都不差）。

测试目录里除了 `cases\` / `args\` / `repl\`，还有一类 `disk\`：一个 `.disk`
文件是对**同一个数据库文件**的一串 acorn 调用，每一行都是独立进程。这是唯一
能证明"数据真的活过了进程边界"的办法——进程一退，内存里的东西就没了，
所以下一行读到的每个字节都只能来自磁盘。

`.disk` 文件里除了"跑一条命令"，还有几种断言：`!pages N`（文件正好几页）、
`!bytes N`（正好几个字节）、`!exists` / `!missing NAME`（某个文件在不在）。
`!exists test.db-journal` 和 `!missing test.db-journal` 在阶段 5 之后到处都是
——**它们断言的是一条不变式（"有没有没结的账"），不是文件管理的细节**。

阶段 6 又多了三个，用来把**第二个进程**放进测试里：

```
!bg 2500|SQL     后台起一个 acorn：跑完 SQL 之后把库多开 2500 毫秒
                 （--hold）再退。脚本会一直等到它打出 [--hold] 那一行
                 才往下走——**它说它拿住了，才算拿住了**。
!wait            等它跑完，把它说的话抄进基准
!killbg          不打招呼地杀掉它（= 任务管理器里的"结束任务"）
```

**为什么不睡一会儿了事**：因为"睡 500 毫秒它应该已经起来了吧"是一个
有时过有时不过的测试，而**一个会偶尔失败的测试比没有测试更糟**——
它训练人不去看失败。所以后台进程自己喊一声"我准备好了"，测试去等那一声。

非零的退出码会记成 `! exit N`（0 不记，不然基准里全是噪音）。
它是**脚本唯一看得见的东西**，所以值得钉住：

```
! exit 1      SQL 写错了 —— 重试多少次都一样
! exit 2      命令行/环境有问题 —— 等一会儿重试可能就好了
              （文件名写错、文件不是 Acorn 格式、库被别的进程占着）
```

```powershell
.\tests\run_tests.ps1            全部跑一遍
.\tests\run_tests.ps1 -Update    重新生成基准输出
```

> `-Update` 会老老实实把**当前的实际输出**写成基准。它能跑通不代表结果是对的——
> 生成完必须自己读一遍，否则等于把 bug 录进了基准文件里。

## 支持的 SQL

```sql
CREATE TABLE users (id INT, name TEXT, score REAL, active BOOL);

INSERT INTO users VALUES (1, 'alice', 91.5, TRUE);
INSERT INTO users VALUES (2, 'bob', 78.0, FALSE);
INSERT INTO users VALUES (3, 'carol', NULL, TRUE);

-- 查询
SELECT * FROM users;
SELECT id, name FROM users WHERE score > 80;
SELECT name FROM users WHERE score > 80 AND NOT (name = 'bob');
SELECT NOT active, -score FROM users;            -- 选择列表里可以写表达式
SELECT id, score * 2 + 1 FROM users;             -- 表达式可以嵌套
SELECT id AS 编号, score * 2 AS 双倍 FROM users;  -- 别名
SELECT id FROM users WHERE score IS NULL;        -- 判空只能这么写
SELECT id FROM users ORDER BY score DESC, id ASC LIMIT 3 OFFSET 1;
SELECT score * 2 AS 双倍 FROM users ORDER BY 双倍 DESC;   -- 别名能排序

-- 聚合
SELECT COUNT(*), COUNT(score), SUM(score), AVG(score), MIN(name), MAX(id) FROM users;
SELECT COUNT(*) AS 人数, AVG(score) AS 平均分 FROM users;   -- 聚合最需要别名

-- 改和删
UPDATE users SET score = score + 5 WHERE id = 1;
UPDATE users SET name = 'x', score = 0;          -- 没有 WHERE 就是改全表
DELETE FROM users WHERE score IS NULL;

-- 删表
DROP TABLE users;

-- 索引
CREATE INDEX users_id ON users (id);
SELECT * FROM users WHERE id = 3;        -- 走索引
SELECT * FROM users WHERE id > 90;       -- 也走索引
SELECT * FROM users WHERE id > 10 AND id < 90 AND active = TRUE;   -- 一半走索引
DROP INDEX users_id;
DROP TABLE users;                        -- 连带删掉它的所有索引

-- 事务
BEGIN;
INSERT INTO users VALUES (4, 'dave', 60.0, TRUE);
UPDATE users SET score = 0 WHERE id = 1;
ROLLBACK;                                -- 上面两条一起撤销

BEGIN;
DELETE FROM users WHERE score < 60;
COMMIT;                                  -- 上面这条此刻才真的生效

-- 不写 BEGIN 的话，一条语句自己就是一个事务
INSERT INTO users VALUES (5, 'erin', 88.0, TRUE);   -- 跑完就生效了

-- 事务里 DDL 和 DML 混着写也行
BEGIN;
CREATE TABLE 备份 (id INT, name TEXT);
INSERT INTO 备份 VALUES (1, 'alice');
ROLLBACK;                                -- 建表和插入一起撤销
```

**索引能帮上忙的条件，和帮不上忙的：**

| 条件 | 走索引吗 |
|---|---|
| `WHERE 索引列 = 值` | ✅ |
| `WHERE 索引列 > / >= / < / <= 值` | ✅ |
| 值写在左边（`WHERE 5 = id`） | ✅ 认得出是同一个条件 |
| 顶层 `AND` 串起来的 | ✅ 能用的那部分用上 |
| `OR` / `NOT` / `!=` | ❌ 退回全表扫 |
| 列在两边（`WHERE id = k`）、列被表达式包住（`WHERE id + 1 = 4`） | ❌ 退回全表扫 |
| `IS NULL` / `IS NOT NULL` | ❌ 退回全表扫 |
| 表小的时候 | 用不用都行，结果一样 |

退回全表扫**从来不是错误**，只是慢。`index_planner_fallback.sql` 把上面
每一行的"❌"都测了一遍——因为规划器认错了方向才是真出事的那个方向。

- **类型**：`INT` / `REAL` / `TEXT` / `BOOL`
- **字面量**：整数、小数、`'字符串'`（单引号，`''` 转义）、`TRUE` / `FALSE` / `NULL`
- **比较**：`=` `!=` `<>` `<` `<=` `>` `>=`、`IS NULL` / `IS NOT NULL`
- **逻辑**：`AND` `OR` `NOT`
- **算术**：`+` `-` `*` `/` `%`、一元 `-`
- **优先级**（从松到紧）：`OR` → `AND` → `NOT` → 比较 → `+ -` → `* / %` → 一元 `-` → 括号
- **聚合**：`COUNT(*)` / `COUNT(列)` / `SUM` / `AVG` / `MIN` / `MAX`
- **别名**：`表达式 AS 名字`，只在 `ORDER BY` 里可见
- **排序分页**：`ORDER BY 键 [ASC|DESC], ...` + `LIMIT n [OFFSET m]`
- **注释**：`-- 到行尾` 和 `/* 跨行 */`
- **大小写**：关键字、表名、列名一律不敏感（`SELECT` / `select` / `SeLeCt` 一样）
- **标识符**：可以是中文（`CREATE TABLE 学生 (姓名 TEXT);`）

**保留字**：`ORDER`、`AS`、`DROP`、`INDEX`、`ON`、`BEGIN`、`COMMIT`、`ROLLBACK`
是关键字，不能再用作列名。
这是加 `ORDER BY` / `AS` / `DROP TABLE` / `CREATE INDEX` / 事务
必须付的代价——每加一个关键字都要想一遍它会占用掉哪个名字。
阶段 4 一口气加了两个（`INDEX` 和 `ON`），代价是 `CREATE TABLE index (on INT)`
这种写法没了；阶段 5 加了三个事务关键字，`CREATE TABLE commit (begin INT)`
同理也写不了了。

**刻意不支持**（留给后面的阶段）：`JOIN` / `GROUP BY` / `HAVING` / 子查询 /
`INSERT ... SELECT` / `NULL` 以外的约束 / 多列索引 / 唯一索引 /
保存点（`SAVEPOINT`）/ 事务嵌套 / 并发。

### SQL 语义里几条必须说清楚的

**`COUNT(*)` 和 `COUNT(列)` 不是一回事。** 前者数行数，后者数这一列里
**非 NULL** 的个数。上面那张表里 `COUNT(*)` 是 3 而 `COUNT(score)` 是 2。
用 `COUNT(列)` 去数行数，是 NULL 一多就出错的经典写法。

**所有聚合函数都忽略 NULL，`COUNT(*)` 例外。** 最反直觉的后果是 `AVG`：
它不是"和 ÷ 行数"，而是"和 ÷ **非 NULL 的个数**"。分数是 90 / NULL / 80 时，
`AVG` 给 85 而不是 56.7——"不知道他多少分"不该把平均分往下拉。

**空集上的聚合有个不对称**：`COUNT` 给 `0`（"有几个"确实是 0），
`SUM` / `AVG` / `MIN` / `MAX` 给 `NULL`（"一堆空值的和"没有答案）。
如果 `SUM` 给 0，那 `SELECT SUM(x) FROM t WHERE 1=0` 和"真的和为 0"就分不开了。

**`= NULL` 永远是 `UNKNOWN`，筛不出任何行。** 不报错——这是 SQL 最著名的坑。
要筛 NULL 只能用 `IS NULL` / `IS NOT NULL`，它们是唯一返回真布尔而不是
`UNKNOWN` 的判空写法。测试里的 `is_null.sql` 专门把这个坑演示了一遍。

**`ORDER BY` 里 NULL 当最小值。** 所以升序时 NULL 冒头、降序时沉底。
这是跟 SQLite 学的；Postgres 的默认正好相反。没有"对错"，但必须选一个并写下来。

**整数除法向零截断**：`7 / 2 = 3`，`-7 / 2 = -3`（不是 Python 的 `-4`）。
**`%` 的符号跟着被除数走**：`-7 % 2 = -1`，`7 % -2 = 1`。

**`AVG` 永远返回浮点，`SUM` 保持整数。** `AVG(1, 2)` 是 `1.5` 不是 `1`——
整数截断会让它算错。而 `SUM` 一列整数必须得一列整数，转成浮点的话
超过 2^53 就开始丢精度。两者不可兼得时，各自选了自己更需要的那个。

**`UPDATE` 的 `SET` 右边读到的全是改之前的值。**
`UPDATE t SET a = b, b = a` 真的能交换两列，不会出现"改完 a 之后 b 读到的是新 a"。
实现上就是先把所有新值算完，再一起写回去。

**`UPDATE` 里同一列写两次，后面的赢**（`SET score = 1, score = 2` 得到 2）。
所以 `SET` 存的是有序的 `vector` 而不是 `map`——用 `map` 的话
第二条会静悄悄地覆盖掉第一条，用户就看不到自己写错了。

**别名只在 `ORDER BY` 里可见，`WHERE` 里看不见。** 这不是偷懒，是标准 SQL：
执行顺序是「先 `WHERE` 筛选 → 再算 `SELECT` 的列 → 最后 `ORDER BY` 排序」，
所以筛选的时候别名还不存在。`SELECT id AS n FROM t WHERE n = 1` 会报
"没有叫 n 的列"，这个报错是对的。

**别名和真实列名撞了的时候别名赢。** `SELECT score AS id, name FROM t ORDER BY id`
排的是 `score`，不是真的 `id` 列——和标准 SQL 一致。
这是个会咬人的歧义，`alias.sql` 专门把它测出来了，
让它的行为至少是**确定的**而不是看运气。

**不支持省略 `AS` 的别名**（`SELECT score s FROM t` 是语法错误）。
因为省略写法会让一个常见笔误静悄悄地合法：`SELECT name score FROM t`
（少打一个逗号）会变成"一列叫 score 的 name"，而且不报错。
宁可不支持，也不要让笔误有个看起来合理的解释。

**除零和整数溢出一律报错，不返回 NULL 也不回绕。**
除零是跟 Postgres 学的（SQLite / MySQL 会给 NULL）；选报错是因为
NULL 会静悄悄地传染到后面的计算里。
溢出必须报错是因为 C++ 里 signed 溢出是**未定义行为**（不是"回绕"，
回绕是 unsigned 才有的保证），放着不管是真的会算出莫名其妙的数。
`SUM` 溢出同样报错，报错信息里带上"累加到多少时又加了多少"——
聚合是个累积过程指不出"哪两个数"，但这两个数足够用户去表里定位了。

**`DROP TABLE` 删的是"这张表"，不是"这些页"。** 表在目录里的那条记录被划掉
（留个墓碑），它占的页挂回空闲链，等着下一次 `CREATE TABLE` 捡走。
所以 `DROP` 之后文件**不会缩小**——把文件截短是另一件事，还没做。
能捡回来这件事本身是 `drop_free_reuse.disk` 在测的：连删带建四次，
页数一直是 3，最后一次没有可捡的才长到 4。

**`DROP TABLE` 连带删掉这张表上的所有索引。** 不连带的话，索引里存的行号
指向的是**已经还给空闲链的页**——那些页随时会被别的表拿去用，
索引就成了指向别人数据的指针，而且查起来不报错。
（真数据库里 `DROP TABLE` 要写 `CASCADE` 才删依赖对象，是因为还有视图、
外键那些**独立**对象。索引不算独立对象，它是表的一部分，所以各家都直接一起删。）

**索引对同一个值可以有很多条。** `CREATE INDEX i ON t (k)` 之后插入 400 行
`k = 5`，索引里就有 400 条键看起来一模一样的项，而且它们**会跨好几个叶子页**。
这能work是因为键其实不是 `k`，是 `(k, 行号)` 这个复合键——
只按键找的话，走到一个叶子页发现"这一页的键都等于目标值，但没找到我要的那一行"
时，就不知道该往右走还是停下，跨页的重复键会**静悄悄地丢**。
`index_big.disk` 里那张 400 行同值的表就是为这个存在的。

**索引列上没写条件就不走索引。** `SELECT * FROM t WHERE name = 'x'` 在
`name` 上没有索引时，和建索引之前一模一样——全表扫，答案不变。

**建索引当下会扫一遍全表。** 不扫的话，索引只对"建完之后新插的行"有效——
那时候 `WHERE id = 1` 走索引**查不到已经存在的那一行**，结果少了行而且不报错。
真数据库建索引慢，慢的就是这一趟。

**`UPDATE` 改了索引列，索引项跟着搬。** 老键按**老值**删掉、新键按新值插进去；
行要是撑大搬了家（行号变了），索引项里存的行号也跟着换。
这一条是整条写路径上最容易出错的地方——错了的话回表会读到墓碑或者**别人的数据**，
一声不响。`index_grow_move.disk` 专门把它逼出来。

**不敲 `BEGIN`，每条语句自己就是一个事务。** 这条规则叫自动提交
（autocommit），是所有 SQL 数据库的默认行为。它有个很不显眼但很值钱的
后果：**一条改到一半失败的语句不会留下痕迹**。
`UPDATE t SET b = a` 改到第 3 行才发现整行装不下时，第 1、2 行已经改过了——
但那条语句自己回滚，所以表还是原样。这条是 `txn_statement_atomic.repl`
在盯着的（那里第 1、2 行真的被改过，不是"还没来得及改"）。

**没提交的事务，进程退出时会被撤销，而且会提醒你一句。** 这和 SQLite 一致：
关掉程序不等于提交。所以屏幕上会多一行"事务还开着，没有 COMMIT"。
**不替你提交**是刻意的——一个"退出就自动保存"的数据库会让
"没提交 = 还没定"这句话变成谎话，而事务的全部价值就在这句话上。

**显式事务里一条语句出错，事务本身不动。** 只有那条语句自己回滚，
前面几条还在事务里，用户改一下重敲就行。（自动提交的那条语句出错时，
整个隐式事务回滚——因为那个事务里只有它一条。）这也和 SQLite 一致。

**`COMMIT` / `ROLLBACK` 时没有事务开着就是错误。** 报的是
"现在没有事务可以提交（要开事务得先敲 BEGIN）"，而不是一句通用语法错。
用户敲出这一条，九成是以为自己前面那句 `BEGIN` 还开着。

**事务不能嵌套。** `BEGIN` 套 `BEGIN` 直接报错，没有保存点。
真数据库里嵌套靠的是 `SAVEPOINT`，那是另一套东西（可以只撤一半），
这一阶段不做。

**提交之后日志文件就没了，这不是副作用，这就是提交本身。**
`<库文件>-journal` 在不在，是"有没有一笔没结的账"的唯一判据。
所以测试里到处是 `!missing test.db-journal` 和 `!exists test.db-journal`
——它们断言的是一条不变式，不是文件管理的细节。

## 数据是怎么落到磁盘上的

### 一页长什么样

整个存储的最小单位是 **4096 字节的一页**。文件就是很多页首尾接起来，
第 N 页的偏移永远是 `N * 4096`——**页号能直接算出偏移，所以文件里不存页号**。

一张表的数据页用的是一种叫**槽位页（slotted page）**的结构。它要同时解决
两个矛盾的需求：变长的行、和"这一页里还有多少缝"。

```
 +--------------------------------------------------+
 |  页头 12 字节                                     |
 +--------------------------------------------------+
 | 槽位0 | 槽位1 | 槽位2 | ...         → 往页尾长 →  |
 +--------------------------------------------------+
 |                 ↑ 空闲区 ↓                        |
 |  ← 往页头长 ←        cell2 | cell1 | cell0        |
 +--------------------------------------------------+
                                                4096
```

一页里每个字节是什么意思，精确到偏移：

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 1 | 页类型（`FILE_HEADER` / `CATALOG` / `HEAP` / `FREE`）|
| 1 | 3 | 保留（对齐用，将来放标志位）|
| 4 | 4 | 下一个页号，没有就是 `INVALID_PAGE` |
| 8 | 2 | 槽位数组里有几项（**含墓碑**）|
| 10 | 2 | `cellTop`：cell 区已经用到的**最低**偏移 |
| 12 | 4 × 槽位数 | 槽位数组，每个槽 = 偏移(2) + 长度(2)，往页尾长 |
| `cellTop` | | cell 区，从第 4096 字节**倒着往前长** |

**空闲字节数 = `cellTop - (12 + 槽位数 × 4)`。**
（文件被改坏的时候这个减法会回绕成一个巨大的数，然后插入会以为空间无限大
往页外写。所以 `heapFreeBytes` 里卡了一道：`cellTop` 比槽位数组末尾还小就
返回 0。**"能不能算出一个数"和"这个数能不能用"是两件事。**）

- **页头 8 字节是三种页共用的**：第 0 字节是页类型，第 4 字节是"下一个页号"。
  空闲页链要用 `next`，一张表的所有数据页也要用 `next`——三种页的其余部分
  完全不一样，但这 8 个字节形状一样，于是"沿着链走"这件事可以只写一份代码。
  **这就是"页"这个概念的用处**：不管里面装什么，从外面看都是一样大的、
  可以互相串起来的一块。
- **页号能直接算出偏移**（`页号 × 4096`），所以文件里任何地方都不存页号。

真正存一行的那块字节叫一个 **cell**。cell 里是这条记录的每个字段，每个字段
前面 1 个字节写"这格是什么"：

```
0x00 NULL   （后面什么都没有）
0x01 INT    （8 字节）
0x02 REAL   （8 字节）
0x03 TEXT   （4 字节长度 + 字节内容）
0x04 BOOL   （1 字节）
```

**为什么要带类型标记**：不给每格标类型的话，"这一格里存的是 NULL、还是 0"
就分不开了——`COUNT(列)` 数的正是这个区别，NULL 格子必须能被认出来。
另一个好处是解码不用回头看表结构，坏掉一个字节不会让整个解析错位到不可收拾。

`RowId` 就是 `(页号, 槽位号)` 这一对。要读一行，先顺着表的数据页链走到那一页，
再查第几个槽，两步都是 O(1)。

### 页缓存：64 格，时钟算法

磁盘 IO 一次要等几毫秒，而内存里挪 4KB 只要几十纳秒。所以每次读写都直接
打到文件上，跑一个扫全表的查询就慢得没法看。中间必须垫一层缓存。

Acorn 的页缓存是 **64 格，一块连续内存（256KB），时钟（second-chance）淘汰**：
每格有一个"被用过"的标记，要腾地方时从指针处转圈扫——标记是 1 就清成 0 继续转，
标记是 0 就淘汰它。这样**经常用到的页会一直转不到**，新页也进得来。

- **借出（pin）**：谁拿到一页的指针，这一页就不许被淘汰。缓存交出的是一个
  RAII 句柄，句柄活着的时候页是钉住的，析构时自动还回去——`return` 提前退出、
  抛异常，都不会漏掉 unpin。手动 unpin 的话，每一处提前 `return` 都是一个坑。
- **写回不是立刻的**：改了页只标一个"脏"字，等这一页被淘汰时才真写磁盘。
  所以 `.info` 里那个"待写回"的数字会攒着。同一个页改一万次，磁盘只写一次。
- **句柄里存着格子编号**，还的时候是 O(1)，不用去 64 格里找。

`.info` 就是让你看这一层的：

```
库的位置：my.acorn
缓存 3/64 格在用，其中 0 页待写回、0 页被借出；文件共 3 页
```

**这是唯一能看见缓存的地方**——没有它，"缓存到底有没有起作用""页漏没漏"
就只能靠猜。

### 空闲页：DROP 掉的空间去哪了

文件头里存着一个**空闲页链表的头**。`DROP TABLE` 把表的数据页一个个挂进这条链，
`CREATE TABLE` 需要新页时先去链上取。链表是用页自己的字节串的——
页已经没人要了，正好拿它的头 4 字节存下一个空闲页的页号。

这条链表要是断了，程序**不会报错也不会崩**，只会慢慢地、看不出来地把磁盘吃光。
所以它只能靠断言页数来测——`drop_free_reuse.disk` 里那几行 `!pages`
就是在盯这个：（删了再建）应该是 3，不是 4。

### B+ 树：索引长什么样

索引是一棵 **B+ 树**。它不是另起炉灶的一套东西——节点就是页，页头还是
那 8 个字节，还是槽位页，只是页类型换成了 `BTREE_LEAF` / `BTREE_INTERNAL`。
一页装不下就分裂成两页，树长高一层就多一个根。所有叶子页用 `next` 串成一条链，
所以"从 5 扫到 90"这件事，找到一个起点之后就是**顺着链往右走**，
不用回到根重新找路。

```
                    [ 50 | 120 ]                 内部节点：只有键和子页号
                   /      |      \
          [ 5 20 40 ]  [ 50 70 90 ]  [ 120 200 ]   叶子页：键 + 行号
               ↕             ↕             ↕         （↕ 是 next 链）
```

**键不是"列的值"，是 `(列的值, 行号)`。** 这一点是整棵树能work的前提，
下面设计决定 27 单独讲。

**内部节点里的键是"抄上来"的，不是"挪上来"的。** 一个叶子页分裂时，
右半边最小的那个键**复制**一份到父节点，原来那一份还留在叶子里——
因为真正带行号的那条记录必须待在叶子页上（内部节点只负责指路）。
内部节点分裂时不一样：右半边最小的键是**推**上去的，推上去之后它
在下面就不再需要了，所以父节点里那个条目只有子页号、没有键（`BTREE_NO_KEY`）。

**这个"抄 vs 推"的区别直接决定了删除可以做得多简单**，见设计决定 28。

### 回滚日志：怎么把改了一半的东西退回去

**问题的形状**：脏页是攒着写的。程序好好跑完没问题，但有两种情况会让文件
停在"一半改了、一半没改"：

1. 一条语句跑到一半失败（`UPDATE` 改到第 3 行才发现装不下）；
2. 进程在写回的过程中没了（掉电、被 kill）。

两种情况的解法是同一个：**改之前先把"原来的样子"记下来**。

就在库文件旁边放一个 `<库文件>-journal`，里面按顺序记着
「第几页 + 它原来的 4096 字节」。要退的时候照着写回去，再把文件切回
事务开始时的长度（事务可能让文件变长，那些新页得整个切掉）。

```
my.acorn          库文件（改的是它）
my.acorn-journal  回滚日志（改之前先在这儿留一份旧的）
```

★ **整个阶段 5 的命根子是这一条不变式** ★

> **某一页的新内容写进库文件之前，它的旧内容必须已经在日志里。**

顺序反了的话，库文件已经改成新的了，日志里却没有旧的——这时候崩溃就再也退不
回去了，那才是真正的数据损坏。所以每一次往库文件写页（提交时的批量写、
缓存淘汰时的单页写）之前，都要先把日志刷到磁盘。这个"刷"不是
`fflush`（那只是交给操作系统，操作系统自己还有一层页缓存），是
`_commit` / `fsync`（真的交给磁盘）。

**这是"为什么数据库需要 fsync"最具体的例子**：不是因为怕丢数据，
是因为**顺序**。两次写之间没有这道闸门，顺序就是操作系统说了算，
而它不知道哪一次更重要。

**崩溃恢复没有"接着做完"这个选项。** 回滚日志里只有**旧**内容——
崩溃前那些新改动只存在于内存里，磁盘上没有，没法补。所以下次打开时
唯一能做的事就是**退回**，回到事务开始前那一刻，做完把日志删掉。
（能"接着做完"的是重做日志（redo log），那是另一个设计。两种日志都能
保证原子性，区别是崩溃后往哪个方向走。）

**日志头读不出来时，程序一个字都不改。** 日志文件存在 ≠ 日志写完整了。
写到一半掉电，头可能是半截的，而那半截里的"文件原来有几页"是**任意一个数**，
照着它切会把库文件切坏。所以头里的魔数和校验和对不上就报错退出，
**宁可不修，也不能猜**——猜错的代价是把本来还好的数据改坏。
（`txn_bad_journal.disk` 里那个 `!bytes` 断言证明的就是"一个字节都没写"。）

### 一个进程退出时

既然脏页是攒着写回的，退出时得有个地方把攒的写完——`Pager` 的析构函数会把
所有脏页刷下去、关掉文件。所以"插完就退出"和"插完 `.quit`"落盘的东西一样。

但**析构里做的第一件事是看事务还开着没有**：开着就回滚（顺带提醒一句），
关着才轮到刷脏页。这个顺序不能反——先刷后滚的话，中间那一小段窗口里
磁盘上躺着的是一个"没提交却已经生效"的状态。

## 好几个进程一起用同一个库

### 先说清楚这一阶段做的是什么

Acorn 能被人看见的表面只有"一个进程、一条连接"。所以这里的并发**必须跨进程**
才谈得上真假——不然就是自己跟自己抢，怎么写都是对的。

**做的是锁，不是 MVCC。** 一句话说清区别：

- **锁**：读的时候别人不能写，写的时候别人不能读。简单，看得见，
  代价是一个慢查询会把所有写者拦在门外。
- **MVCC**（多版本）：每个读者看自己的一份**快照**，读写互不阻塞。
  PostgreSQL、InnoDB 走的是这条路，代价是每个版本都得留着、还得有人清理。

这一阶段做的是**前者**，而且不打算含糊其辞地假装它是后者。MVCC 是另一个设计，
不是这个设计"再加一点"。

### 锁放在哪：一个单独的 `<库文件>-lock`

```
my.acorn          库文件
my.acorn-journal  回滚日志（阶段 5）
my.acorn-lock     锁文件（阶段 6，永远是 0 字节）
```

**为什么不锁库文件本身**：Windows 的文件锁是**强制**的（mandatory），
不是建议性的。锁住库文件的字节范围，就等于告诉操作系统"这些字节别让别人读写"——
于是连正常的读都会莫名其妙地失败。锁一个谁也不读的 0 字节文件，
"谁在用这个库"和"库里的数据"就分开了，互不干扰。

**"锁文件存在"不等于"库被锁着"。** 这是个反直觉但很重要的事实：
锁文件是**建完就一直留着**的，从第一次打开起它就在那儿（0 字节）。
"被锁着"是**内核里的状态**，不是文件里的字节。所以删掉锁文件不能解锁，
它还在那儿也不能说明有谁在用。判据只有一个：**能不能锁上**。

### 为什么必须是"内核给的锁"，不能自己写一个

自己写的话，最自然的做法是往 `.lock` 文件里写一个进程号：进来先读，
进程号还活着就说明有人在用。

这条路有一个绕不过去的问题：**被强杀的进程没机会删掉那个文件**。
任务管理器点"结束任务"、掉电、`TerminateProcess`——都不跑任何析构、
不刷任何缓冲。于是那个文件变成一个**僵尸锁**：库里明明没人在用，
后来的人却谁也进不去。

要修就得判断"那个进程号还活着吗"，而 **Windows 会把进程号回收再分配**：
一个早就死掉的号可能已经属于别人了。判断错了就是两个写者同时改一个文件——
回到了没有锁的状态，还多了一层"它看起来是好的"。

操作系统的文件锁没有这个问题，因为**放锁是内核做的**：进程一消失
（不管怎么消失的），它持有的锁全部立刻释放。没有需要人去清理的残留，
也没有"进程号还活着吗"这个不可靠的问题。

`lock_released_on_kill.disk` 就是钉这一条的：后台进程开好事务、
写了一半，然后被 `!killbg` 直接杀掉；下一条命令**立刻**就能用，
顺手还照日志把没提交的那一行退掉了。

### 什么时候拿、什么时候放

| 时刻 | 锁 |
|---|---|
| 打开库 | **共享**（"我要读"） |
| `BEGIN`（含不敲 `BEGIN` 时的自动提交） | **独占** |
| `COMMIT` / `ROLLBACK` 之后 | 退回**共享** |
| 进程结束 | 内核自动全放 |

**升级的时机是"事务开始"，不是"第一次写"。** 这一点值得单独说：

一条 `UPDATE ... WHERE ...` 里**读和写是混在一起的**——先扫出符合条件的行，
再改它们。如果等到真要写的那一刻才升级，那么前面那段扫就是**没有锁保护的读**：
扫到一半别人把行改了，改完之后你再写回去，那是一个经典的丢更新
（lost update）。所以打开事务的那一刻就把写的位置占住。

**升级绝不在内核里干等。** 两个都拿着共享锁的进程如果都想升级，
就是死锁：谁都等着对方先放手，谁都不肯。所以规则是
**"抢不到就去掉自己那把、然后报错"**，让用户决定要不要重试。
宁可报错，不可死锁。

### 被挡住的时候，用户看到什么

默认**不等待**，当场报错，而且是两句话分开的两件事：

```
错误：库 my.acorn 现在有别的进程开着，写不了它——要改数据就得等那个进程关掉。（想等一会儿的话，加 --lock-wait=毫秒）
错误：库 my.acorn 现在被另一个进程独占着（它正在写），连读都不行。（想等一会儿的话，加 --lock-wait=毫秒）
```

第一句是"别人在**读**，你要**写**"，第二句是"别人在**写**，你连**读**都不行"。
区别值得分清楚：第一种只挡住写者，第二种会把所有人都挡住——包括只想
`SELECT` 一下的人。第二种是这一阶段最该被记住的代价。

愿意等就加 `--lock-wait=毫秒`，等不到会告诉你**等了多久**：

```
错误：库 my.acorn 现在有别的进程开着，写不了它——……（等了 400 毫秒也没等到）
```

那个数字是用户自己给的那个。不然他没法判断是自己等太短，还是程序压根没等。

**退出码是 2，不是 1。** 这不是随手定的，见下面「退出码」那一段。

### 恢复必须拿着独占锁做

崩溃恢复是彻头彻尾的一次写（把旧内容写回库文件、再截短）。共享锁下做这件事，
等于和另一个也拿着共享锁、也准备恢复的进程同时动库文件。

所以顺序是死的：**先锁，再恢复，再打开**。每一步都在为下一步排除掉一种
"别人也在动"的可能。

还有一个**先拿锁、再看状态**的顺序问题：升级成功之后，要**再确认一遍**
日志还在不在。等锁的这段时间里，别人可能已经把这件事做完了
（他先拿到独占锁、恢复完、删了日志、放锁走人）——这时候我们手里这把锁
来得很及时，但要说的事已经没了。

反过来（先看状态、再拿锁）看到的永远是过期的状态。这个错误有个名字，
叫 check-then-act，它的修法永远是同一个：**把检查挪到锁里面**。

### 退出码：脚本唯一看得见的东西

人看的是"错误：……"那句话，脚本看的是退出码。所以它是 API：

```
0   一切正常
1   SQL 写错了 —— 重试多少次都一样
2   命令行/环境有问题 —— 等一会儿重试可能就好了
```

"库被占着"属于第 2 种。但它在代码里有**两个被发现的位置**：
一个是开库的时候撞上（那时还没跑到 SQL，自然落在"打开失败"那一类），
另一个是库已经开着、敲到 `BEGIN` 要升级独占时才撞上（这时错误是从
**语句执行**里冒出来的，默认会被归成"SQL 的问题"）。

同一个问题报出两个不同的数，脚本就没法据此判断该不该重试了。
所以"库被占着"在代码里是一个**独立的异常类型**（`BusyError`），
两条路都认它，两条路都给 2。为什么不靠比对错误文案：那等于把提示措辞
当成 API，改一个字的措辞就悄悄弄坏一个调用方。

### 路径：一个字节都不该被猜

这一阶段顺手补掉一个真 bug，它和并发无关，但是**锁这一层把真相带出来的**。

Acorn 内部一律用 UTF-8 存字符串。而 Windows 上 C 标准库的 `fopen` / `remove` /
`std::ifstream` 收的是**窄字符**，走的是**系统 ANSI 代码页**（这台机器上是 GBK）。
把 UTF-8 的 `测试库.db` 交给 `fopen`，它不会说"我不认识"，它会**拿 GBK 去解释
那串 UTF-8 字节**，于是去找一个名字完全不同的文件。

症状因此特别难查：

```
$ acorn.exe -d 测试库.db -e "CREATE TABLE t (id INT);"
错误：建不了数据库文件：测试库.db（目录不存在？没有写权限？）
```

目录明明在。真正发生的是：UTF-8 里一个汉字三个字节、GBK 里两个，
所以解码会**错位**；错位之后只要有一个字节是 `0x5C`，它就成了反斜杠，
路径被切到了别的目录。

最坏的情况不是报错，而是 GBK 恰好拼出一个合法名字——那就会**悄悄建出另一个
文件**，程序一切正常，用户下次拿自己的名字去开，发现数据没了。

**发现它的线索是一个"能建、一个不能建"的对比**：库文件建不出来的时候，
同一目录下那个 `测试库.db-lock` 却好好地建了出来。因为锁那一层从一开始
就是用 `CreateFileW`（宽字符 API）写的，而库文件那边从头到尾用的是 `fopen`。

修法见 `utf8path.hpp`：所有碰路径的地方统一走一层 UTF-8 → UTF-16，
再调宽字符版本（`_wfopen` / `_wremove`）。路径是**文件的名字**，
猜错一个字节找的就是另一个文件——这种事上没有"将就一下"的余地。

## 代码结构

从上到下是一条直线，每一层只认识它下面那层：

| 文件 | 干什么 |
|---|---|
| `text.hpp/.cpp` | 显示宽度（中文占 2 格）、右填充 |
| `value.hpp/.cpp` | 值的表示与类型检查 |
| `error.hpp/.cpp` | 两类错误 + 带箭头的错误渲染 |
| `token.hpp/.cpp` | Token 定义、大小写归一 |
| `tokenizer.hpp/.cpp` | 词法分析：SQL 文本 → Token 流 |
| `ast.hpp/.cpp` | 语法树节点 + 访问者接口 |
| `parser.hpp/.cpp` | 语法分析：Token 流 → 语法树 |
| `ast_printer.hpp/.cpp` | 访问者实现 ①：把树打印回 S 表达式 |
| `schema.hpp/.cpp` | 列和表结构 |
| `utf8path.hpp/.cpp` | **路径是 UTF-8，而 Windows 的 `fopen` 认 GBK**——所以碰路径的地方统一走这一层 |
| `page.hpp/.cpp` | **一页 4096 字节里，第几个字节是什么意思**（槽位页、行编解码、目录记录） |
| `pager.hpp/.cpp` | **这 4096 字节从哪来、什么时候写回去**（页缓存、脏页、空闲链）|
| `journal.hpp/.cpp` | **改之前先留一份旧的**（回滚日志、fsync 顺序、崩溃恢复）|
| `lock.hpp/.cpp` | **这个库现在归谁**（跨进程的文件锁、读/写两种模式、升级与降级）|
| `btree.hpp/.cpp` | **B+ 树**：插入、删除、按区间查、分裂 |
| `table.hpp/.cpp` | 一张表：数据页链、扫描、插入、更新、删除 |
| `database.hpp/.cpp` | 一堆表 + 一堆索引：目录页的读写、建表删表、建索引删索引、**表与索引一起改的写入口** |
| `executor.hpp/.cpp` | 访问者实现 ②：遍历语法树干活 |
| `main.cpp` | REPL / 脚本运行 / 命令行 |
| `result.hpp` | 执行结果 |

`page` 和 `pager` 是阶段 3 插进来的两层，位置很讲究：

- **`page` 不知道文件的存在**。它拿到的就是一个 `char*`，指向 4096 字节，
  它只管往这段内存的哪个偏移写什么。所以这一层的逻辑可以拿一块
  `std::vector<char>` 就测，不需要磁盘。
- **`pager` 不知道页里装的是什么**。行、表结构、空闲链，对它来说都是
  4096 个字节。所以它可以把"缓存""脏页""写回"当成纯粹的数据搬运来做。
- **只有 `pager` 碰文件内容**。整个 `src/` 里已经没有 `fstream` 了：
  所有文件操作都收在 `pager`（库文件和脏页写回）和 `journal`（日志）里，
  而它们又都统一经过 `utf8path` 那一层出去。
  所以"什么时候真正落盘"是一个能一眼看完的问题。
  锁文件是个例外，但它**不装数据**：`lock` 碰的是"谁在用"，
  和"库里有什么"完全是两件事。

这两条约束是刻意维持的：布局规则是**不该变**的（改了旧文件就读不出来），
"从哪来"是**将来一定要变**的（阶段 5 加了日志、阶段 6 加了锁）。
把善变的东西和不该变的东西放在一个文件里，早晚会一起变。

阶段 5 加 `journal` 这一层的时候，这两条约束各自兑现了一次：

- **`journal` 不知道库文件是文件还是内存库。** `forEachRecord` 只负责
  "把记下来的每一页交出来"，怎么落到库文件上是 `Pager` 的事。
  所以内存库照样有事务（`ROLLBACK` 和"一条语句要么全做要么全不做"
  在内存库上一样要有），只是日志记在内存里。
- **`pager` 仍然不知道页里装的是什么。** 日志把它变成了"写这一页之前
  先留个底"，而这和页里是行、是表结构、是 B+ 树节点毫无关系。

阶段 6 加 `lock` 的时候兑现的是同一句话的第三次：**`lock` 不知道库文件的
内容**。它只管一个 0 字节的锁文件，连库文件有多大都不需要知道。
所以它对 `page` 里那套布局、对 B+ 树、对事务语义全都一无所知——
换成任何一个"需要一个跨进程的独占/共享"的程序，这一层都能原样搬走。

`pager` 里那句 `getForWrite` 是这一层的门：**要改一页，就得从这道门进**。
门里做两件事——开事务（如果没有）、把这一页的旧内容记进日志。
`markDirty()` 那里放了一道检查，谁绕开这道门直接改页，程序会当场报
「内部错误：……是被改过的，但它没有先经 getForWrite 记进日志」。
**这道检查就是那条不变式本身**，不是它的近似物：能不能"绕过"它，
和能不能破坏不变式，是同一件事。

`btree` 插在 `pager` 和 `database` 之间，位置同样是按那条规矩定的：

- **它不知道"表"的存在。** 它只认识"键"和"行号"，
  不知道键是从哪一列来的、行号指向的又是什么。所以它可以脱离表单独测。
- **它是无状态的句柄。** 一个 `Btree` 对象里只有 `(pager, 根页号, 键类型)`
  三样东西，真正的状态全在页里。所以"根页变了"这件事不需要同步两处——
  每次现造一个，状态就只有一份。

`executor.cpp` 里那段"规划器"（`planCondition` / `planIndex` / `scanWithPlan`）
待在执行器那一层，不在 `btree` 里也不在 `table` 里，也是刻意的：
**它是"这个条件怎么问才便宜"的问题**，而这个问题只有同时知道
"有哪些索引"和"条件长什么样"的人才答得上来。`btree` 只管"给我一个区间、
我还你一批行号"，它没有资格决定要不要用它。

`ast_printer.cpp` 的存在本身就是"访问者模式有没有用"的答案：
它和执行器毫无关系，却完整复用了同一棵语法树，一行节点代码都没改。

`RowId` 从 `size_t`（第几行）换成 `(页号, 槽位号)` 的时候，
执行器**一个字都没改**——因为它从头到尾只把 `RowId` 当不透明的句柄
传来传去。阶段 1 那个 `using RowId = size_t;` 里留下的缝，这里是兑现的时候。

## 几个刻意的设计决定

### 1. `Table::scan()` 收回调，不返回 `vector`

```cpp
void scan(const std::function<void(RowId, const Row&)>& visit) const;
```

阶段 1 把所有行放在内存里，返回 `const std::vector<Row>&` 是最省事的写法。

但阶段 3 要把行搬到磁盘上，一行一行从 4KB 的页里读出来——那时候
"所有行"根本不存在，没法返回一个 vector。

改成回调，执行器那一层**一个字都不用动**。这是 Acorn 的 `shared_ptr` 时刻：
为已经看得见的需求多留一层，比事后重写便宜得多。
（Nova 里对应的一幕是 `Environment` 从第一天就用 `shared_ptr`。）

**阶段 2 先收了一次利息**：`UPDATE` / `DELETE` 需要"知道改的是第几行"，
所以 `scan` 顺带把 `RowId` 也交给回调。

**阶段 3 把本金也收了**：`RowId` 从 `size_t`（第几行）换成了
`(页号, 槽位号)`，而**执行器那边一个字都没改**——它从头到尾只把 `RowId`
当不透明的句柄传来传去（从 `scan` 接过来、原样传给 `update`）。
要是阶段 1 图省事让执行器自己去数"这是第几行"，阶段 3 就是一场大改。
**判断一个接缝留得对不对，就看换实现的时候有多少调用方要动。**

### 2. 语法树用 `unique_ptr`，不是 `shared_ptr`

Nova 里必须用 `shared_ptr`：闭包返回之后，它那次调用的作用域还得活着，
而且多个闭包可能指着同一个作用域——所有权不唯一。

SQL 的语法树是**纯树**：每个节点有且只有一个父节点。所有权唯一的时候，
`unique_ptr` 才是对的——它表达的信息更强（"我独占这个孩子"），开销更小，
而且天然不可拷贝，编译器会帮你挡住"手滑复制了一棵子树"。

**先问所有权唯不唯一，再决定用哪个智能指针。**

### 3. `SELECT` 的列存的是表达式，不是列名

```cpp
std::vector<SelectItem> columns;   // 不是 std::vector<std::string>
```

阶段 1 只支持 `SELECT name, score`，存列名就够了。但阶段 2 要支持
`SELECT score * 2`、`SELECT COUNT(*)`，那时候每一项都是表达式。

**这笔前瞻已经兑现了**：阶段 2 加这些功能时，`SelectStmt` 的这个字段
一个字都没改，改动全集中在 parser 里。代价是阶段 1 多写了一点
（每次取列都要 `accept` 一次），收益是阶段 2 没有一次四文件联动改动。

**然后阶段 2 收尾加 `AS` 时它改了**——从 `vector<ExprPtr>` 变成
`vector<SelectItem>`（表达式 + 别名）。这是那层前瞻的**真实边界**：
它让"往表达式里加东西"变便宜，但"往列表项上加东西"还是得动结构。
好在只动了 4 处（parser 填、executor 读两处、printer 读），
没有全项目铺开。**前瞻降低改动的成本，不是消除它**——
把它当成"以后什么都不用改"就过头了。

### 4. `NULL` 走真正的三值逻辑

SQL 的 `NULL` 意思是**"不知道"**，不是"空"。

```
NULL = NULL        →  NULL   （不知道等于不知道，仍然是不知道）
NOT NULL           →  NULL
TRUE AND NULL      →  NULL
FALSE AND NULL     →  FALSE  （短路：左边已经是假，右边是什么都不影响结论）
```

所以 `WHERE name = NULL` **一行都不返回**——想判断 NULL 得用 `IS NULL`（阶段 2）。
同理 `WHERE NOT (name = 'a')` 会把 `name` 为 NULL 的行滤掉，
因为 `NOT NULL` 还是 NULL，而 `WHERE` 只放行**确定成真**的行。

`tests/cases/null.sql` 专门盯这件事。

### 5. 类型不同就报错，不做隐式转换

`WHERE id = 'a'`（整数和文本比）在 Acorn 里是**错误**。

别家数据库往往会定一套"类型优先级"（比如 SQLite 规定数字永远小于文本），
然后给你一个答案。我们不这么干——静悄悄给个答案，错误会跑到离现场
很远的地方才发作，到时候根本查不出来。

唯一的例外是 `INT` → `REAL`：无损加宽，放行。反过来（`1.5` 塞进 `INT` 列）报错。

### 6. `WHERE` 后面必须是布尔值

`WHERE id`（`id` 是整数）报错，不像 C 那样"非 0 即真"。

理由是同一个：`WHERE id` 大概率是 `WHERE id = 1` 写漏了，与其猜，
不如让你说清楚。

### 7. 错误走 stderr，正常输出走 stdout

这样 `acorn f.sql > 结果.txt` 不会把报错混进结果文件里。

代价是得处理缓冲：`std::cout` 带缓冲、`std::cerr` 不带。两个流汇到同一个
地方时，不先 flush 一下 `cout`，错误信息会跑到它前面那批正常输出的**前面**去，
看起来像"错误发生在还没执行到的地方"。见 `main.cpp` 的 `printError()`。

### 8. 列名重复在**建表时**就拦住

```sql
CREATE TABLE t (id INT, id TEXT);   -- 报错，不建
```

要是放过去，后面 `SELECT id` 到底取哪一列就没法说了。
检查在解析阶段做（`parser.cpp`），因此**报的是语法错误**，箭头指向后出现的
那个重复列名——该改的是它。

`CREATE TABLE order (...)` 在阶段 1 能过，因为那时 `ORDER` 还不是关键字。
**这个雷在阶段 2 已经拆了**：`ORDER` 现在是保留字，再加 `ORDER BY` 之后
`SELECT * FROM t ORDER BY x` 会被正确解析，而不是被理解成
"从表 t、表 order、表 by 里查"。见 `err_keyword_order.sql`。

### 9. 运算符的优先级完全由**调用嵌套**决定

递归下降解析器里没有一张"优先级数值表"，一层函数就是一级：

```
expression → orExpr → andExpr → notExpr → comparison
           → additive → multiplicative → unary → primary
```

`additive()` 要解析一个 `+` 的右边时调的是 `multiplicative()`，
**调用关系本身就编码了"乘法比加法紧"**。这样加新运算符时只需要把它插进
链条的某一层，不用去维护一个会和代码脱节的数值表——
数值表最容易出的错是两个人同时用 `3` 当优先级。

### 10. 一元 `-` 从 `primary` 挪到了 `unary`

这是阶段 2 加算术时发现的一个**已经存在的 bug**：阶段 1 一元负号待在
`primary` 里，而 `primary` 里没有乘法，所以 `-x * 2` 会被解析成
`-(x * 2)`——负号先吃掉了整个 primary，表达式结构就错了。

挪到 `unary`（在 `multiplicative` 下面一层）之后，`-x * 2` 正确地变成 `(-x) * 2`。
`ast_phase2_unary.args` 把这条钉住了（`-a % 2` 打出 `(% (- a) 2)`）。

**"加新运算符时，旧运算符该不该换层"是改语法时最容易漏掉的事**——
因为旧的那个单看没错，只有和新的一起用才暴露。

### 11. 聚合走的是另一条路，不是逐行求值

普通表达式是"给我一行，算出一个值"。聚合不是——`COUNT(*)` 要看到
**所有**行才能给出答案，单独一行算不出"总数"。

所以 `visitSelect` 先扫一遍全表，把结果累加进 `aggregateStates_`，
**扫完之后**才去求值选择列表。那时候 `visitCall` 不再是"计算"，
而是"取已经算好的结果"。

两个并行数组一一对应：`aggregateNodes_[i]` 这个调用节点，
它的累加器是 `aggregateStates_[i]`。**用指针做对应关系而不是下标**，
因为调用节点藏在表达式的任意深度（`COUNT(*) + 1` 里的 `COUNT`
就不是选择列表的第一项），没法用位置去猜。

累加器 `AggregateState` 是个**纯数据袋子**——它不记录"我是 MIN 还是 MAX"，
因为那个信息在调用节点上（`aggregateNodes_[index]->name`）。
把身份和数据分开，累加器就不用跟着聚合种类一起增删字段。

### 12. `SUM` 空集给 `NULL`，`COUNT` 给 `0`

同一次扫描、同一份累加器，两个函数在空集上给不同的答案。这是标准 SQL，
而且是对的：`COUNT` 问的是"有几个"，空集答 `0` 是个确定的答案；
`SUM` 问的是"加起来多少"，空集没有答案。
如果 `SUM` 也给 `0`，那 `SELECT SUM(x) FROM t WHERE 1=0` 和
"这一列真的加起来等于 0"就分不开了，用户没法区分"没有数据"和"数据是零"。

### 13. `SET` 存有序 `vector`，不是 `map`

`UPDATE t SET score = 1, score = 2` 是合法的，后者赢。
用 `map` 的话第二条会静悄悄地覆盖掉第一条——**结果一样，但用户
看不到自己写了重复的列**。存 `vector` 就能在需要时报出来。
（现在没报，只是照后者执行。要不要报是个可以再想的问题。）

### 14. `UPDATE` 先把所有新值算完，再一起写回去

```sql
UPDATE t SET a = b, b = a WHERE id = 1;   -- 真的能交换两列
```

如果边算边写，`b = a` 读到的就是**已经被改过的新 a**，交换就失败了。
实现的顺序是：扫描时把命中的 `(行号, 新行)` 全部收进一个 vector，
扫完再逐个 `updateRow`。这和 `Table::insert` 里"先全部校验再 push"
是同一条原则——**不要在一个会被打断的过程中留下中间态**。

### 15. 别名靠"替换表达式"实现，不是靠"改名查找"

`SELECT score * 2 AS 双倍 FROM t ORDER BY 双倍` 里，`ORDER BY 双倍`
不是去表结构里找一列叫 `双倍` 的，而是**在算排序键的时候把
`双倍` 换成它背后的那棵 `score * 2` 子树**（见 `resolveAlias`）。

这么做的直接好处是：排序用的和显示出来的**是同一个表达式**，
不可能出现"显示的是一回事、排序按另一回事"。
如果改成"先算出显示值、再拿显示值排序"，这两条路就会各自演化，
早晚对不上（比如显示时做了类型转换、排序时没做）。

代价是别名的作用范围必须**明确划出来**——现在只在 `ORDER BY` 里开这个口，
`WHERE` 里不开。不划的话迟早有人以为 `WHERE` 里也能用。

### 16. 别名不支持省略 `AS`

`SELECT score s FROM t` 是语法错误，必须写 `AS`。

省略写法在别的数据库里合法，这里**故意不实现**，因为它会让一个
常见笔误静悄悄地合法：

```sql
SELECT name score FROM t     -- 少打了一个逗号
```

用户想选 `name` 和 `score` 两列，实际得到一列叫 `score` 的 `name`，
**而且不报错**。加了 `AS` 之后这一行会老老实实报语法错误，
正好提醒他少了个逗号。

「宁可不支持一个便利写法，也不要让笔误有个看起来合理的解释」——
和 `WHERE` 后面必须写布尔值是同一条原则。

### 17. REPL 判断"写完了没有"，靠的是 Token 而不是找分号

阶段 1 的 REPL 用 `pending.find(';')` 判断语句结束，
于是 `INSERT INTO t VALUES ('a;b')` 会在**字符串中间**那个分号处提前执行，
报一句莫名其妙的"字符串没有收尾的单引号"。

改法是问词法分析器：`scanTokens()` 之后看**最后一个 Token** 是不是分号。
分号的语义在 tokenizer 里已经定死了，在 REPL 这边再猜一遍
就是"同一个规则有两处实现"——它们早晚会分叉。

**真正麻烦的是"分析不了"该怎么办。** 两种情况混在一个 `SyntaxError` 里：

```
SELECT * FROM t WHERE name = 'abc     ← 没写完，报警是错的
SELECT ! FROM t                       ← 写错了，就该现在报
```

所以加了 `IncompleteError`（`SyntaxError` 的子类），只用在
**字符串没收尾**和**块注释没收尾**这两种"再敲几个字符就能自愈"的情况：

- 是 `IncompleteError` → 静静继续攒，一个字都不报
- 是别的 `SyntaxError` → 立刻报出来，并清空缓冲

清空缓冲那一步也是想过的：REPL 没法回头改已经敲过的行，
留着那段坏文本只会让提示符卡在 `...>`，用户以为还在等他补完。
丢掉、报错、提示符回到 `acorn>`，是唯一说得通的行为。

因为它继承 `SyntaxError`，脚本模式和 `-e` 模式的
`catch (const SyntaxError&)` 行为一个字都没变——
在那些地方输入已经全部到手，没写完就是错了。
**加一个子类，而不是加一个 bool 参数，就是为了让这条分界线落在类型上。**

## 阶段 3 的设计决定

下面接着上面的编号。前面 17 条全是语法树 / SQL 那一层的，
这 9 条是存储那一层的——它们大都不是"怎么写更漂亮"，
而是"两个都对的做法里选哪个，以及另一个的代价由谁付"。

### 18. 一行不跨页

一行的字节必须能塞进一页（上限 4080 字节），塞不下就报错。

代价是 `TEXT` 列不能无限长。收益是**读一行只需要读一页**——
不用把好几页拼起来，不用担心"行读到一半发现缺了后半截"。
SQLite 的做法是溢出页（一行跨多页），那是在"行可以很长"和
"一页能读完"之间选了前者、再想办法补回来。Acorn 选了后者。

这个上限是算出来的，不是拍出来的：`4096 - 12(堆头) - 4(槽位) = 4080`。
报错信息里直接写这个数，用户就知道自己超了多少。

### 19. 槽位页：把"行的身份"和"行的位置"拆开

一张表里的行**长度不一样**（`TEXT` 有长有短）。如果行挨着行顺序排，
删掉中间一行，后面全得往前挪——**而且 `RowId` 会跟着变**，
所有拿着 `RowId` 的人全傻了。

槽位页把这两件事拆成两块：

| | 管什么 | 能不能动 |
|---|---|---|
| 槽位数组 | 第 n 行在哪（4 字节：偏移 + 长度）| **下标永不变**，那是 `RowId` |
| cell 区 | 字节放哪 | 随便挪，反正槽位知道新地址 |

于是删除 = 把槽位长度改成 0，别的一动不动。**第 3 行永远是第 3 个槽位**，
不管中间删了多少行。

`heapUpdate` 是这套设计兑现价值的地方：新值变长时，老位置立成墓碑、
另找地方放、槽位指向新位置——**槽号没变**，所以 `RowId` 还指着同一行。
判据是「哪个东西的身份是它的位置」：cell 的偏移没人记得住（每次现查槽位），
所以能动；槽位的下标就是身份本身，所以不能动。

### 20. 槽位数组永不缩短，墓碑的 4 字节是永久代价

空间回收只回收 cell 区（`heapCompact` 把活着的 cell 重新贴到页尾），
**槽位数组不缩**。删了 20 行就永远多占 80 字节。

本来想顺手把末尾的墓碑截掉，想了一下不行：截掉之后，一个持有旧 `RowId`
的调用方再按那个槽号去读，会读到**另一个活着的行**——它以为自己拿到了
老数据，其实是别人的数据，而且不报错。留着墓碑的话，同一个 `RowId`
读到的稳定是"这行没了"。

**报错比"给了个错答案但不报错"好得多。** 用一个永远收不回来的
4 字节/墓碑，换"死 `RowId` 只会报死，不会指到别人身上"，这个价付得起。

### 21. 不存能算出来的东西：页数 = 文件大小 ÷ 4096

文件头里**没有**"文件一共多少页"这个字段。一开始写了，后来删掉了：
文件有多大文件系统自己就知道，再记一份就有了两个真相来源。两者一旦
对不上（写到一半断电、手工改过文件大小），程序该信谁？没有好答案。

**凡是能问出来的信息就别存。** 这条和 `schema` 里"不存 key、只存 name"
是同一个原则，只是这次删掉的是一整个字段。

（这个决定直接决定了测试怎么写：`!pages N` 断言的是**文件的字节数**，
所以它同时也验证了"页数算得对"。）

### 22. 每个值带 1 字节类型标签，不存空值位图

位图方案省 1 字节/列（"第 3 格是 NULL"一个 bit 就够了），但那样解码时
**必须拿着表结构才能读**——字节流不自描述。哪天表结构变了（加了一列），
旧数据用新结构去解，会把字节解释成完全不同的东西，而且**读得出来**，
只是值是错的。

自带标签的话，读到不认识的标签就能当场报"数据文件坏了"。
**一个数据库最怕的不是报错，是不报错但答案不对。** 多花的那 1 字节/列
买的就是这个。（另外 NULL 必须能被认出来——`COUNT(列)` 数的正是它，
这个区别是功能，不是省不省字节的问题。）

浮点用 8 字节**位模式**存，不用文本。文本存法要处理"打印几位小数"，
而 `double` 有 17 位有效数字，打印成文本再读回来经常差一点点——
差一点点在钱和数据上就是事故。

### 23. 小端是写死的，不靠"碰巧和本机一样"

`readU16` / `writeU32` 这些函数是一个字节一个字节拼的，不写
`*reinterpret_cast<uint16_t*>(p)`。那个直觉写法有两个问题：

1. **对齐**：`char*` 可能落在奇数地址上。本机 x86 容忍，所以现在这么写
   也能跑——然后换台机器就炸。
2. **严格别名规则**：编译器有权假设 `uint16_t*` 和 `char*` 指的不是同一块内存，
   从而把读写重排掉。

显式拼字节两头都不占，而且**认字节序**：在小端机和大端机上读出来的数一样。
数据库文件是要跨机器读的，"碰巧本机是小端"不是一种格式。

### 24. 缓存淘汰用时钟，不用 LRU

64 格的缓存，一块连续内存（256KB）。要腾地方时从指针处转圈扫：
"被用过"标记是 1 就清成 0 继续转，是 0 就淘汰它。

真 LRU 要维护一条"最近使用"的链表，每次取页都动链表指针；
时钟算法用一个 bit 加一个转圈指针，近似出同样的效果——
**经常用到的页会一直转不到**，新页也进得来。代价是实现上的确定性
换了几十行代码和每次取页的常数开销。

写回也是攒着的：改了页只标一个"脏"字，等这页被淘汰时才真写磁盘。
同一个页改一万次，磁盘只写一次。所以 `.info` 里那个"待写回"会攒着——
**它是唯一的窗口**，没有它就只能靠猜"缓存到底有没有起作用"。

### 25. 取页必须拿借条，标脏必须显式

**不能返回 `char*`。** 调用方正往这页里写，缓存另一次取页把这一页踢出去、
位置让给了别的页——那个 `char*` 还在原地写，写的却是另一页的内容。
**不会崩**，只是数据静悄悄地坏掉。这是最难查的一类 bug。

所以取页给的是一张借条（`Pager::Handle`）：构造时 pin 住，析构时还回去。
提前 `return`、抛异常，都不会漏掉 unpin——手动 unpin 的话每一处提前
`return` 都是一个坑。借条里还直接记着"我在缓存第几格"，
所以还的时候是 O(1)，不用去 64 格里找（unpin 是这程序里最热的一行）。

标脏是**显式**的（`markDirty()`），不自动。因为绝大多数取页是只读的
（全表扫描把每一页都读一遍），自动标脏会让扫一遍整张表就把所有页标成
待写回，接着一次 flush 把没改过的页重写一遍——磁盘白写，
而且是在最不该慢的时候慢。

### 26. 内存库模式不是"测试开关"，它把接口约束住了

`Pager` 的 `path` 为空就是内存库。两个用处：

1. **测试**：跑一遍 SQL 脚本结果必须每次都一样。要是默认就往文件里写，
   第二次跑就会看到上次的数据，基准输出根本没法写。
2. 它就是 SQLite 的 `:memory:`，本来就是个正经功能。

顺带它还逼出一件事：这一层的接口只跟**页**打交道，不跟**文件**打交道
（没有 `fseek`、没有文件名参数、没有"这个表存在哪"）。
这个约束是好东西，所以哪怕只有一个用处也值得留着。

## 阶段 4 的设计决定

接着上面的编号。前面 26 条是语法和存储的，这 10 条是索引的——
它们几乎都在回答同一个问题：**加了一棵会跟着数据一起变的树之后，
怎么保证它和表永远对得上。**

### 27. 键是 `(值, 行号)`，不是光一个值

这是整个阶段 4 里最重要的一个决定，也是最容易漏的一个。

B+ 树的查找是"在节点里二分找最后一个 ≤ K 的位置"。如果键只有"值"，
那么在一棵有重复键的树里，这个规则会**指错方向**：

```
叶子页 A: [ 5 | 5 | 5 ]        叶子页 B: [ 5 | 5 | 8 ]
要查 k = 5 的**所有**行。走到 A 的最后一个 5，
"最后一个 ≤ 5 的位置"就是这一页的最后一条 —— 该往右走吗？
不知道。因为 B 里也是 5，而"往右走"的判据是"这一页的最后一个键 ≤ K"，
在 A 上成立，在任何一个装满了 5 的页上都成立 —— 会一直往右走到天边。
```

加上行号当**第二排序键**之后，整棵树里就没有两个相等的键了
（同一行的同一个列只有一个值，`(值, 行号)` 唯一）。
于是"找最后一个 ≤ K"变成一个**全序**上的二分，方向永远明确，
重复键跨多少个叶子页都能一条条扫完。

代价是键长了 6 个字节（页号 4 + 槽位 2）。**这 6 个字节买的是"重复键不会丢"**——
而重复键在真实数据里到处都是（性别、状态、城市、日期）。
`index_big.disk` 里 400 行同值的那个测试就是拿这个当靶子的。

顺带：因为键里已经含了行号，**索引天然是唯一的**，
不需要额外处理"同一个键插两次"。

### 28. 删除不合并、不借位 —— 空掉的叶子页就让它空着

教科书的 B+ 树删除要处理"节点太空了":找兄弟借一个条目，或者和兄弟合并，
再把父节点里的分隔键删掉。这些代码又长又难测。

Acorn **不做这些**，而且这不是偷懒，是因为上面那个"抄上来 vs 推上来"
的区别让删除**不需要**它们：

```
内部节点:  [ ... | 50 | ... ]      50 这个键是当年左孩子分裂时**抄**上来的。
             /          \          它左边的所有键都 ≤ 50，右边的都 ≥ 50 ——
      [ ... 30 40 ]  [ 50 60 ... ]  这个不等式在那些键被删掉之后**依然成立**。
```

删掉左孩子里那个 40 之后，父节点里还留着 40 的话会怎样？查找 `k = 40`
会走到左孩子，在里面找不到 —— 结果是"没找到"，**这是正确答案**。
分隔键只要还满足"左边 ≤ 它 ≤ 右边"，它就还是个能用的路标；
它对应的那条记录不在了，只说明查它查不到东西。

所以删除就只是"把叶子页里那一条抹掉"。叶子页空了呢？**留在链上**，
只是里面一条都没有了。它占的那一页不回收——和墓碑那 4 个字节是同一个取舍：
**宁可浪费一页，也不要写一段"移动数据、改父节点"的代码，
然后花三天去证明它在所有情况下都对。**

（这个取舍的代价是真实存在的：反复插入又删除，文件会一直涨。
真要收紧，加的是"空闲页回收"，不是"合并"。）

### 29. 两条目录链，不是一条

索引也需要落盘，而且比表更需要：**B+ 树的根页号要是没记下来，
下次打开就是一棵谁也找不到的树**（里面的页还在文件里，但没有任何东西指向它们）。

所以文件头里现在有**两个**链头：

```
偏移 20：表目录链   ->  表名、列、第一个数据页
偏移 28：索引目录链 ->  索引名、表名、列号、根页号
```

为什么不挤在一条链上？因为两条链里的记录**形状完全不同**，
而记录格式里**没有"这条是什么"的判别字节**。挤在一起的话，
要么给每条记录加一个判别字节（等于改已有记录的格式，旧文件全读不出来），
要么让读的人靠猜。分开之后，各自的记录格式就是自己的事。

代价是打开库要扫两遍链。目录通常只有一页，这个代价是零。

（有个细节是刻意对齐的：**两种记录都把页号放在偏移 1**——
表记录是"第一个数据页"，索引记录是"根页号"。这样"改一条记录的页号"
那几行代码两种记录能共用。这个便宜是白捡的，因为当初排字段时
把页号放在最前面本来就是合理的选择。）

### 30. 规划器只有一条契约：结果一个字都不能变

```cpp
// scanWithPlan：先用索引找出候选行的行号，再按 (页号, 槽位) 排一遍序
std::sort(ids.begin(), ids.end());
```

加索引的唯一目的是让查询变快。**快多少是可以商量的，答案对不对不能商量。**
所以走索引的那条路必须和全表扫给出**完全一样**的输出——包括行的顺序。

索引的遍历顺序（按键排）和全表扫的顺序（按页号、槽位号）是两回事。
不排那一下的话，`SELECT * FROM t WHERE id > 3` 有没有索引会打出不同的行序，
测试基准立刻就不一样了——而这种差异一旦被"嗯，反正是无序的"糊弄过去，
真正的问题（比如漏行）就会混在里面看不出来。

排一下的代价是 O(n log n) 的排序，但 n 是**命中的行数**而不是全表行数，
而且它换来的是"有没有索引，输出字节完全一致"这个可以说死的性质。

### 31. 执行器拿不到 `Btree`

```cpp
void searchIndex(..., const std::function<void(RowId)>& visit) const;
```

这是执行器能对索引做的**唯一**一件事——它没有办法拿到 `Btree` 对象本身，
也就不可能绕过"表和索引一起改"这条规矩去动树。

边界划在**类型**上，不是划在"谁能拿到 Btree"这种约定上。
约定靠自觉，类型靠编译器：想绕过去，得先改头文件。
（同一个思路在别处也用过：`Pager` 交出来的是借条不是 `char*`；
`Table` 的槽位下标外面拿不到。**能靠类型挡住的错误，不要靠注释挡住。**）

### 32. 索引维护放在 `Database` 的写入口

```cpp
db_.insertRow(表名, 行);          // 插表 + 更新这张表上所有索引，一次做完
db_.updateRow(表名, 行号, 行);
db_.deleteRows(表名, 行号列表);
```

执行器**不再直接碰 `Table`**。原因很简单：一次写要同时落在两个地方
（表的数据页、这张表上所有索引的 B+ 树），分开做的话，任何一条路径漏掉
索引维护，表现都是"索引和表对不上"——而那种坏是**不报错**的坏。

所以"维护索引"这件事被放在拥有这两样东西的人手里（`Database` 同时管着
表和索引）。这和"校验行的类型"被放在 `Table` 里、"槽位下标不许外面动"
被放在 `page.cpp` 里是同一条原则：**不变式由拥有它的人来守**，
别人连碰都碰不到，就不存在"忘了一次"。

`Database` 里面那几个函数还各自有个不显然的顺序：

- **`insertRow`：先插表，再插索引。** 因为 `Table::insert` 会**就地**把
  `INTEGER` 补宽成 `REAL`，后插索引才能拿到补型之后的值。
  （为了这个，`insert` 的签名从 `void insert(Row)` 改成了 `RowId insert(Row&)`——
  按值传的话，调用方看不到那个被改过的行。）
- **`updateRow`：老键必须在改之前读。** 改完再读"老值"读到的是新值，
  于是索引里那条老记录永远删不掉，从此查老值会查出一行**已经不是那个值**的行。
- **`DELETE`：同理，删之前先把整行读出来。**

### 33. 分裂点按**字节数**找，不是按"对半分"

一个叶子页满了要分裂，从哪儿切开？最省事的写法是"切一半"（`n / 2`）。
但 B+ 树的条目是**变长**的（`TEXT` 键长度差很多），按条数对半分的话，
可能切出 200 字节的一边和 3800 字节的一边——那一页马上又满了。

所以分裂点是一个**前缀和搜索**：把每个条目的字节数累加起来，
找一个位置让"左边总字节数"和"右边总字节数"最接近，
并且两边都得装得进一页。代价是分裂的时候多一次 O(n) 的扫描——
分裂本来就是 O(n) 的（要重排整页），所以这是白捡的。

### 34. 根页号会变，所以它必须能被写回去

树长高一层，根就换了一页。**这个新根页号如果不写回目录记录，
下次打开这个库就只有半棵树**——新的根在文件里，但文件头里没有它，
于是它上面那一层永远找不到。

所以 `IndexInfo` 里存了"这条索引的目录记录在哪"（页号 + 页内偏移），
每次插入之后检查一下根页有没有变，变了就回去把记录里那 4 个字节改掉。

那条目录记录的位置是**建索引的时候顺手记下来的**，不是事后去找的。
找也能找到（重新扫一遍索引目录链），但每插一行都要扫一遍目录——
而这个信息在我们自己写它的时候本来就知道。**顺手记下来比事后找便宜。**

### 35. 建索引要先量一遍所有键长，失败要失败得干净

`CREATE INDEX big_v ON big (v)` 遇到一个装不下的值时会报错。**报错本身不难，
难的是报错之后不能留下东西**——半棵建好的树、半条目录记录，
留下了的话这个库以后每次打开都会去读一棵不存在的树。

所以 `createIndex` 的顺序是刻意排的：

1. 先量目录记录多长（但不写）
2. **扫全表把每个键都量一遍** ← 长度不够的在这里就报出来了
3. 才开始分配页、建树
4. 最后往索引目录里追一条记录

也就是说，**任何会失败的事都排在第一次写之前**。
这和解析器的"先全部解析、再执行"是同一条原则，
只是这次的对象从语句变成了键。
`index_key_too_big.disk` 测的就是这个：报错之后重开进程，
表还在、索引一个都没有、那个名字也没被占住。

### 36. 文件格式版本从 1 涨到 2

索引目录链的头用了文件头里偏移 28 的 4 个字节——那是阶段 3 留的保留区。
**旧文件那 4 个字节是 0**，而 0 是个**看着合法的页号**（第 0 页，
也就是文件头那一页）。程序会拿它当"索引目录链的第一页"去读，
读出来的是一堆垃圾字节，然后按垃圾去解析。

所以版本号必须涨。校验在读文件头的时候就会把版本 1 的文件挡掉，
报"格式版本是 1，本程序只认 2"——**说清楚而不是硬着头皮读**。
`err_bad_file.disk` 盯着这条。

（这里有个连带教训写在下面"坑"那一节：测试里那个"页大小不对"的构造文件
也写着版本 1，版本号一涨，它就先被版本检查挡住了——
**测试还过，只是不再测它声称要测的东西**。）

## 阶段 5 的设计决定

### 37. 用回滚日志，不用影子分页

保证原子性有两条主流路子：

- **影子分页（shadow paging）**：不原地改页，改出来的新页写到别处，
  提交时改一下文件头里"真正的目录"指向新树。旧树整个留着当备份。
- **回滚日志（rollback journal）**：原地改，但改之前把旧内容抄一份到日志里。

选回滚日志，理由是它**不改文件格式**：页号还是 `偏移 ÷ 4096`，
第 N 页还是第 N 页。影子分页要让"逻辑页号"和"物理页号"分家，
整个寻址那一层（`Pager::get` 的每个调用点、空闲链、B+ 树的子页号）
都得跟着变——那是把阶段 3、4 的成果全部推倒重来一遍。

而且日志是**独立于库文件**的一个文件。它坏了、它不存在、它是上次留下的，
这三种情况都能从外面判断出来，不用去解析库文件的内部状态。
（SQLite 默认也是回滚日志，`-journal` 这个后缀就是跟它学的。）

### 38. "提交"这个动作就是**删掉日志**

提交没有别的动作。把脏页写进库文件只是"准备工作"——**只有删掉日志，
这次修改才变成既成事实**。

为什么非要这样？因为崩溃恢复的判据只有一条：**日志还在不在**。
在，就说明上次有个事务没走完，照日志退回去；不在，就一切照常。
日志的存在与否**就是**提交标志位，不需要另外再存一个"我提交了没有"。

这条的直接后果有点反直觉，而且是阶段 5 最值得看的一个测试：
`--crash-at=commit` 让程序在"数据已经全部写进库文件、就差删日志"的那一刻
死掉。这时候的库文件读出来**一切正常**，就是提交后的样子。
但正确的结果是**它必须被整条撤销**——因为日志还在。
`txn_crash_commit.disk` 测的就是这个。

### 39. 事务是**用的时候才开**的，不是语句开始时开的

自动提交最自然的写法是"语句开始时 `begin()`、语句结束时 `commit()`"。
那样写会有一个当场撞上的问题：**用户敲的 `BEGIN` 会被包在那个事务里**，
变成"在一个事务里再开一个"，直接报错。

所以事务是懒开的：**谁第一个要改页，谁就顺手开一个**（`ensureTransaction`）。
`BEGIN` 本身不写页，所以它不会触发；等它之后的 `INSERT` 触发时，
用户那个事务已经开好了（`inTransaction_` 是 true），这里就不会再开。
**一个 `bool` 就把两种情况都覆盖了。**

顺带的好处很实在：只读的语句（`SELECT` 是绝大多数）永远开不出事务，
也就永远建不出日志文件。一份日志都不写，一次系统调用都不花。
这是 `Journal::openIfNeeded` 而不是 `begin()` 里建文件的原因。

### 40. 要改页，就得从 `getForWrite` 这道门进

阶段 3 的取页接口是 `get(pageNo)`，谁都拿得到，谁都改得了。
阶段 5 加了一个 `getForWrite(pageNo)`：门里做两件事——开事务（如果没开）、
把这一页的旧内容记进日志。

**为什么不能"先 `get`，真要改了再补记日志"**：到那时候这一页可能已经被
改过了，"原来的样子"已经没了。所以必须在**交出可写指针之前**记。

代价是这个接口骗不了人：一次只往下走的插入（没分裂）会把路上每一页都
记一遍日志，即使大部分页最后只是被读了一下。这个浪费是**故意的**——
反过来的写法做不到，而做不到的那个是正确性，这个只是效率。

`markDirty()` 那里放了一道检查：`inTransaction_ && pageNo_ < journalPageCount_
&& !journal_.has(pageNo_)` 就抛"内部错误"。这道检查**就是那条不变式本身**，
不是它的近似物：能不能绕过它，和能不能破坏不变式，是同一件事。

> 这道检查在第一次冒烟测试（`BEGIN; INSERT; ROLLBACK`）就抓到了真问题：
> 十几个调用点还在用 `get()` 改页。**让不该发生的事当场报错，
> 比让它悄悄发生强**——那些调用点要是留到后面才发现，症状会是
> "回滚之后数据对不上"，而那时离肇事现场已经很远了。

### 41. 事务要在文件变长**之前**开

`allocatePage()` 分配新页时有一条近路：新页从来没被写过，所以"它原来长什么样"
是已知的（全 0），不用记日志。但**不用记日志不等于不用开事务**——
开事务这个动作还负责记下"事务开始时文件有几页"，而那是回滚时要切回的长度。

所以那句 `ensureTransaction()` 必须在 `pageCount_++` **之前**。
晚一步的话，这个新页就被算进"原来就有"里了，回滚切不掉它——
文件里从此留着一页谁也不认识的垃圾。**而且不会读到坏数据**
（是多了一页而不是少了一页），所以这个 bug 的症状是"每回滚一次建表就漏 4KB，
没人会发现"。这类 bug 只能靠"把顺序写对"来防，测不出来。

### 42. 回滚之后，目录要**重新从磁盘读一遍**

`Database::rollback()` 不只是让 `Pager` 退回页，还要把内存里那份目录
（"有哪些表、有哪些索引"）清掉重读。

因为 DDL 也在事务里。`BEGIN; DROP TABLE t; ROLLBACK;` 之后，
页退回去了，但内存里那份账本还记得"t 被删了"——接下来的查询会去读
一张磁盘上其实还在的表，或者反过来，去读一张磁盘上已经没了的表。
**页和目录是两个真相来源，退了一个就得让另一个重新对齐。**

重新读一遍是最省事的对齐方式：`clearCatalog()` + `loadCatalog()`，
**唯一的真相来源是磁盘**。`txn_ddl.repl` 里的
「错误：没有叫 `gone` 的表（现在有：keep）」就是这一步的证据——
要是没重新读，那句会查到一张不存在的表。

### 43. 崩溃测试用 `_Exit`，不用 `exit`

`--crash-at=commit|exit` 是测试专用开关，模拟"事务中途进程没了"。

用的是 `std::_Exit(1)` 而不是 `std::exit(1)`：`exit` 会跑静态对象的析构、
刷 stdio 缓冲区——**那已经是一次"干净退出"了**，不是崩溃。
`_Exit` 什么都不做，和掉电最接近。（`--crash-at=exit` 那个点就设在
`~Pager` 里、回滚之前，所以它模拟的是"事务开着，进程没了"。）

顺带测出来一个挺好看的性质：**自动提交模式下 `--crash-at=exit` 不会响**。
因为语句跑完就已经提交了，退出那一刻事务是关着的，那个
`if (inTransaction_)` 根本进不去。这不是"没崩"，是"没东西可崩"——
它反过来证明了自动提交真的在自动提交。

## 阶段 6 的设计决定

### 44. 用锁，不用 MVCC

这是整个阶段唯一一个真正的岔路口，所以放在第一条。

**两个选项长这样：**

- **锁**：读的时候不许别人写，写的时候不许别人读。
  实现是"一个进程拿共享锁、一个进程拿独占锁"，几十行代码。
- **MVCC**：每次写留一个新版本，读者按自己的开始时刻看某个版本。
  读写互不阻塞，但要给每一行挂版本链、要有一套"谁还需要这个旧版本"的
  判断和清理（`VACUUM` 那类东西），还要让索引也能回答"哪个版本对这个人可见"。

**选了锁，理由是"能做完并讲清楚"比"功能表更长"重要。**
MVCC 不是"锁加一点东西"，它是另一套数据布局：行里要存版本，
索引项要带可见性信息，事务要有一个全局的时刻表。
半吊子的 MVCC（有版本但没有清理、或者索引不管版本）比老老实实的锁更糟——
它看起来支持并发，实际上会在某些查询上给出错的答案。

**代价写在明面上**：一个长 `SELECT` 会挡住所有写。这是 Mac 上 SQLite
默认的 journal 模式也有的行为，不丢人。README 的已知问题表里也记着这一条。

### 45. 锁放在一个单独的 0 字节文件里，建了就留着

```
my.acorn          库文件
my.acorn-journal  回滚日志
my.acorn-lock     锁文件
```

**为什么不锁库文件本身**：Windows 的文件锁是**强制**的。锁住库文件的字节范围，
等于让操作系统拒绝别人的**读**——包括那些根本没打算抢锁的读
（比如你拿记事本打开看看）。锁一个谁也不读的空文件，
"谁在用这个库"就和"库里有什么数据"彻底分开了。

**为什么锁的是"第 0 个字节"而不是整个文件**：文件锁是按字节范围给的，
锁满整个文件得先知道文件多大，而"多大"以后还会变。
所有进程约定同一个字节就够了，而且**那个字节不必真的存在**——
所以锁文件可以是 0 字节。

**为什么建完不删**：删了也不能解锁（锁在内核里，不在文件里），
所以删它除了制造一次"两个进程在删/建同一个文件"的竞态以外没有任何好处。
留着反而有用：看见 `xxx-lock` 就知道 acorn 开过这个库。
**推论**：`xxx-lock` 存在**不等于**库被锁着。判据只有一个——能不能锁上。

### 46. 升级独占锁时先放掉共享锁，抢不到就报错

`BEGIN` 时要把手里的共享锁变成独占。同一个句柄上放不下两种模式，
所以动作只能拆成"放开 → 抢"。

**那个缝隙是故意的。** 放开的瞬间，别的进程可能抢走独占，于是我们抢不回来、
只好报错。看起来像是"白失败一次"，但另一个做法更糟：

> 拿着共享锁**等**独占锁 —— 两个都拿着共享锁的进程同时想升级，
> 就谁也不肯先放手，谁也等不到。那是死锁，而且**永远**解不开。

所以规则是：**抢不到就报错，让用户决定要不要重试。**
宁可偶尔失败，不可死锁。报错的同时**尽力把共享锁拿回来**
（`FileLock::upgrade` 最后那一段），这样用户在 REPL 里撞上一次写失败之后，
接下来还能继续 `SELECT`——一次写失败不该让整个会话变成残废。

拿不回来也不要紧：状态退成"没有锁"，下次取页时
`Pager::ensureSharedLock` 会再拿一次，拿不到就按"没有锁"报错。
关键是**不会出现"以为有锁其实没有"**。

### 47. 恢复必须在独占锁里面做，而且"看日志"也要在里面

崩溃恢复是彻头彻尾的一次写：把旧内容写回库文件，再截短日志。
两个进程同时做这件事，等于同时改库文件。

所以顺序是死的：**先拿独占锁，再看日志在不在，再恢复，再打开库。**

第二步的**位置**是关键。一个很自然的写法是：

```cpp
if (!journalFileExists(db)) { 打开就好 }
else { 拿锁; 恢复; }
```

这是典型的 check-then-act：**检查发生在锁外面，所以看到的是过期的状态**。
等锁的这段时间里，别人完全可能已经恢复完、删掉日志、放锁走了。
我们手里这把锁来得很及时，但要说的事已经没了——照着不存在的日志去恢复，
轻则白忙，重则按陈旧的记录把已经提交的数据退回去。

修法永远是同一个：**把检查挪到锁里面**。

### 48. "库被占着"是一个独立的异常类型，不是一句话

**退出码是脚本唯一看得见的东西**，所以它是 API：

```
0   一切正常
1   SQL 写错了 —— 重试多少次都一样
2   命令行/环境有问题 —— 等一会儿重试可能就好了
```

"库被占着"属于 2。但它在代码里有**两个被发现的位置**：
开库时撞上（那时还没跑 SQL，自然落在"打开失败"那一类），
和库已经开着、敲到 `BEGIN` 要升级独占时才撞上
（这时错误从**语句执行**里冒出来，默认会被归成"SQL 的问题"）。

同一个问题报出两个数，脚本就没法据此判断该不该重试。所以引入了
`class BusyError : public AcornError`，两条路都认它、都给 2。

**为什么不用字符串匹配**：那等于把提示措辞当成 API——
改一个字的文案就悄悄弄坏一个调用方。**为什么不在 `AcornError` 上加个
`bool busy` 字段**：那种字段总有人忘了设，而"忘了设"的后果是
一个静默的错误退出码，比类型错误难查得多。类型不一样，
编译器会替我们盯着。

### 49. 路径统一走 `utf8path` 那一层

这一条不是设计出来的，是**撞出来的**——但它现在是一条规矩。

Acorn 内部一律 UTF-8。Windows 上 C 标准库的 `fopen` / `remove` /
`std::ifstream` 收窄字符，走**系统 ANSI 代码页**（本机 GBK）。
把 UTF-8 的 `测试库.db` 交给 `fopen`，它不会说"我不认识"，
它会拿 GBK 去解释那串字节，于是去找一个名字完全不同的文件——
中间凑出一个 `0x5C` 就变成反斜杠，路径被切到别的目录。

**最坏的情况不是报错，而是 GBK 恰好拼出一个合法名字**：
那会悄悄建出另一个文件，程序一切正常，用户下次拿自己的名字去开，
发现数据没了。所以这件事上不能"将就一下"。

修法是所有碰路径的地方统一走一层 UTF-8 → UTF-16，再调宽字符版本
（`_wfopen` / `_wremove`）。**规矩定下来之后，`src/` 里就不该再出现
一个裸的 `fopen`**——新增文件操作时照着 `utf8path.hpp` 走。

**发现它的线索值得记一笔**：库文件建不出来（报"目录不存在？没有写权限？"），
可同一目录下的 `测试库.db-lock` 却好好地建了出来。
因为锁那一层从一开始就用的是 `CreateFileW`（宽字符）。
**一个能建、一个不能建**，这个对比就是答案。

| **日志的"删除"没有单独 fsync** | 库文件的页提交前已经 fsync 过；但删日志这个目录操作没刷 | 严格做要再 fsync 一次目录；NTFS 自己记日志，本机碰不到 |
| **是锁，不是 MVCC** | 读会挡住写，写会挡住读；没有快照隔离 | 见设计决定 44。MVCC 是另一个设计，不是"再加一点" |
| **`--lock-wait` 只能在命令行给** | 在 REPL 里撞上"库被占着"，那句提示里的 `--lock-wait=` 当时没法补 | 要能改就得加一条 `.lock-wait` 元命令；现在的办法是等 |
| **升级独占锁可能白失败一次** | 别人恰好在你"放共享→抢独占"的空隙里抢走了 | 刻意，见设计决定 46。宁可偶尔失败，不可死锁 |
| **POSIX 分支没实测过** | `lock.cpp` 里的 `fcntl` 那一支是照文档写的 | 本机只有 Windows；换机器跑一遍测试即可验证 |
| **锁文件建了就留着** | `<库>-lock` 零字节，永远不删 | 刻意，见设计决定 45 |
| **一次只能一个进程开一个库** | ~~两个进程同时写会互相覆盖~~ | **阶段 6 已解决**：见上 |
| **没有保存点、事务不能嵌套** | `BEGIN` 套 `BEGIN` 直接报错 | `SAVEPOINT` 是另一套东西，这一阶段不做 |
| **日志文件是整份副本，没有增量** | 事务里改一页就把整页 4KB 抄进日志 | 真数据库也这么干；WAL 才是省的那条路 |
| **回滚要重放整份日志** | 大事务回滚 = 把记过的每一页写回去 | 现在没有增量检查点 |
| **索引删除不合并、不借位** | 空掉的叶子页留在链上，占着页不还 | 刻意，见设计决定 28 |
| **反复插入+删除会让索引文件一直涨** | 页只还回空闲链，文件不缩 | 缺"截短文件"，不影响正确性 |
| **只有单列索引** | `CREATE INDEX i ON t (a, b)` 是语法错误 | 复合索引要改键的编码和比较 |
| **`OR` / `NOT` / `!=` / `IS NULL` 不走索引** | 退回全表扫，答案不变 | `OR` 要做两趟查找再合并去重 |
| **只有顶层 `AND` 里的条件会被看** | `WHERE (a = 1 OR b = 2) AND c = 3` 里只有 `c` 那部分可能用上 | 要写条件树的重写 |
| **规划器不做代价估算** | 命中率 90% 也照走索引，可能比全表扫慢 | 真数据库靠统计信息，那是另一个阶段 |
| **`CREATE INDEX` 不检查重名的表** | 索引名和表名是两个命名空间，可以同名 | 现在这样不算错，但值得知道 |

**关于"先全部解析、再执行"**：这是刻意的。语法都不合法的脚本，
让它执行一半反而更糟——你会得到一个"改了一半"的数据库，
而且是语法错误导致的。

**执行期的错误现在有两种粒度**，都值得说清楚：

- **一条语句自己**已经是原子的了（自动提交）。`UPDATE` 改到第 3 行才失败，
  前 2 行也会退回去。这是阶段 5 兑现的，`txn_statement_atomic.repl` 盯着它。
- **整个脚本不是**。第 3 句出错时，前 2 句**已经各自提交了**，退不回来。
  想让它整批生效或整批不生效，自己包一层：脚本开头写 `BEGIN;`、
  结尾写 `COMMIT;`，中间出错就整个退回去。

`CREATE INDEX` 失败**不会**留下半棵树（见设计决定 35），
所以"一条语句只做了一半"这种情况现在一处都没有了。

**关于崩溃恢复**：脏页是攒着写的，写到一半断电，磁盘上就会留下一个
"页 3 已经改了、页 7 还没改"的文件——它**能打开**，也能读，
只是内容对应到某个不存在的时刻。现在不会了：下次打开时如果看到日志文件，
就照它退回去，退到一个明确的、事务开始前的状态。

**回滚日志和 WAL 是两条路，别混。** 这一阶段做的是回滚日志：
崩溃后**往回退**。WAL（预写日志）是反过来——先把新内容写进日志，
崩溃后**往前滚**（redo）。两者都能保证原子性，区别是崩溃后往哪个方向走，
以及 WAL 更容易支持"读不阻塞写"这类并发特性。Acorn 的阶段 6 走的是
**加锁**那条路，所以这条缝还留着没被用上。

**关于"一次只能一个进程开一个库"**：这曾经是个**不出声**的坑——
两个进程同时写同一个文件会互相覆盖，而且谁也不报错。现在不会了：
打开库就先拿锁（共享），`BEGIN` 时升成独占，别人占着就报错。
代价是读也会挡住写——见设计决定 44。

**关于"是锁，不是 MVCC"**：说清楚这一条是因为它很容易被含糊过去。
现在的行为是：A 在 `SELECT` 一张大表，B 想 `INSERT` 一行，B 会**报错**。
真数据库（PostgreSQL、InnoDB）在这个场景下 B 会直接成功，因为读者看的是快照。
这是这一阶段最该被记住的取舍，不是 bug，也不是"还没做完"。

**关于 `--lock-wait` 只能在命令行给**：这是个体面的口子，值得写下来。
用户是在 REPL 里撞上"库被占着"的，而那时候命令行已经定好了，
提示里那句"加 `--lock-wait=毫秒`"他补不上——只能等，或者退出去重开。
修法不难（加一条 `.lock-wait` 元命令），但要动 REPL 的状态，
和"这一阶段只想把锁本身做对"冲突，所以留着。

**关于"64 格全被 pin 住"**：这时缓存会抛
「内部错误：页缓存里的 64 个格子全被占住了」。
它不是用户能触发的——正常代码不可能同时按住 64 页（扫描是读一页、
处理完、还回去）。这个报错是给"某个 `Handle` 没被释放"准备的：
把借条存进了成员变量、或者拿了指针忘了作用域。
**缓存大小在这里不是一个调优参数，是一条契约**：超过 64 层嵌套的取页，
程序会明确告诉你，而不是把某一页悄悄换掉。

**关于聚合函数只能待在 `SELECT` 列表里**：这不是偷懒，是逻辑上做不到。
聚合要先把整张表扫一遍才有答案，而 `WHERE` 是逐行判断的、`SET` 是逐行改的，
那些地方根本没有"总数"这个东西可以拿来比。
`SELECT id FROM t WHERE COUNT(*) > 0` 报的不是"没实现"，是"这个问法没有意义"。

**关于没有 `GROUP BY` 时裸列名报错**：`SELECT id, COUNT(*) FROM t` 里那个 `id`
指的是塌缩后的那一行里的哪一行？没法回答。报错是诚实的做法——
猜一个（比如取第一行）会给出一张看着挺正常、但内容是随机的表。

## 一路上的坑（都是这台机器上实测撞到的）

### Windows / TDM-GCC

- **`main(int argc, char** argv)` 里的中文是坏的。** Windows 会把参数转成
  ANSI 代码页（936/GBK）再交给 `main`，信息在那一刻就丢了，事后救不回来。
  解法是绕开 `argv`，用 `GetCommandLineW()` + `CommandLineToArgvW()` 重新取一遍，
  再 `WideCharToMultiByte` 转成 UTF-8。`main.cpp` 的 `collectArgs()` 干这事。
  （`args/eval_cjk.args` 是这个修复的回归测试。）
- **`<shellapi.h>` 必须在 `<windows.h>` 后面。** 它依赖 `windows.h` 定义的
  `EXTERN_C`、`DECLARE_HANDLE` 等宏。按字母序排 include 在这里会炸出一片
  `'EXTERN_C' does not name a type`。
- **`.bat` 文件必须是纯 ASCII。** `cmd.exe` 用 OEM 代码页（本机 GBK）读批处理
  文件，而文件存的是 UTF-8。一个中文字的 3 个字节会被解错，可能把后面的换行
  或脱字符吃掉，行边界就烂了。中文文档放这个 README 里。
- **`.ps1` 文件也必须是纯 ASCII，理由一模一样。** PowerShell 5.1 读一个
  不带 BOM 的 `.ps1` 时用的是系统 ANSI 代码页（本机 GBK），中文会变成乱码，
  而且**报的错和编码毫无关系**：这次是一个中文串里的字节被解成了一个引号，
  于是报 `Missing ')' in method call`，位置指向几行之外。找错的唯一办法是
  拿脚本扫一遍非 ASCII 字节。`run_tests.ps1` 的头注释里早就写着这条，
  我还是踩了——**写在注释里的规矩和写进检查里的规矩不是一回事**。
- **别用 `$out = & $exe ...` 抓输出。** PowerShell 会用
  `[Console]::OutputEncoding`（本机 GBK）解码子进程吐出来的字节，
  中文全成乱码。`run_tests.ps1` 的做法是让 `cmd.exe` 做**字节级**重定向
  写进文件，再显式按 UTF-8 读回来。重定向 `2>&1` 到**同一个**文件还能
  保住 stdout / stderr 的相对顺序——`acorn` 在写 stderr 之前先 flush stdout，
  就是为了让这个顺序有意义。
- **heredoc 会把 `\n` 变成真的换行。** 用脚本生成测试数据文件时，
  `stdin:.tables\n.schema\n` 里那个 `\n` 是**字面量**（测试格式里它表示换行），
  但 heredoc 直接把它展开成了真换行——于是 `.schema` 变成了一行独立的命令，
  程序去开一个叫 `.schema` 的文件，报「打不开文件」。凡是要求字节精确的文件，
  用 `Write` 工具直接写，别过 shell 的引号处理，写完用 `cat -A` 验一遍。
- **`g++ -o a.exe src\*.cpp` 不管用。** `cmd` 不展开通配符（那是 Unix shell 的习惯），
  MinGW 的 g++ 也不展开，于是它收到字面量 `src\*.cpp` 然后报 `Invalid argument`。
  `build.bat` 里那个 `for` 循环就是为此存在的。
- **不要加 `-static-libstdc++`。** TDM-GCC 默认就静态链接 libstdc++（这是它
  相对原版 MinGW-w64 的改动），加了是多余的。

### C++

- **`char` 在本机是带符号的。** 判断 UTF-8 首字节必须先转 `unsigned char`，
  否则中文的 `0xE6` 会被当成负数，`byte >= 0xE0` 永远不成立——中文被当成单字节，
  宽度算成 1，表格全错位。`text.cpp` 里栽过。
- **自由函数里写 `Type::INTEGER` 不认，得写 `Value::Type::INTEGER`。**
  同一个嵌套枚举，能不能简写取决于你在不在类里面——这是作用域查找的规矩。
- **`std::to_string(double)` 是固定 6 位小数**，`3.14` 变成 `"3.140000"`。
  要控制精度得用 `ostringstream`。
- **把超出 `long long` 范围的 `double` 强转成 `long long` 是未定义行为。**
  必须先判范围再转，顺序不能反。`formatNumber()` 里踩过。
- **打印表格不能用 `printf` / `std::setw`**，它们按**字节数**补空格，
  中文会撑破。得用自己的 `displayWidth` / `padRight`。
- **`<windows.h>` 定义 `TRUE` / `FALSE` / `NULL` 宏**，和 SQL 关键字撞。
  Token 枚举里那个 NULL 字面量叫 `NULL_KW` 而不是 `NULL`，就是为了躲开它。
- **中文字符串里千万别写 ASCII 的双引号 `"`。** 它会**直接终止字符串字面量**，
  后面那半句中文就成了游离的代码，报一串 `stray '\xxx' in program`。
  这个坑在写错误信息时踩了三次（`"悄悄回绕"`、`"所有列"`）。
  本项目的约定是：中文错误信息里要强调什么就用反引号 `` ` `` 或
  全角引号 `「」`，**不用 ASCII 引号**。
  （`printf` 的 `%` 也是同类陷阱——错误信息里带 `%` 时别用 `printf` 写文件。）
- **析构函数里不能抛异常。** `Pager::~Pager()` 要把攒着的脏页刷下去，
  而写盘是会失败的（磁盘满、文件被删）。异常一旦穿出析构函数就是
  `std::terminate`——用户看到的是"程序异常终止"，而不是"磁盘满了"。
  所以它自己 `catch` 掉、打到 stderr。**真正的报错机会在调用方显式
  `flush()`**，那才是异常能正常传播的地方。
- **RAII 句柄要禁掉拷贝，只留移动。** 两个 `Handle` 指着同一页的话，
  析构时会 unpin 两次，pin 计数就乱了。这和 `unique_ptr` 是同一个坑、
  同一个写法（`= delete` 掉拷贝，写一个 `noexcept` 的移动）。
  编译器能替你拦住这个，前提是你把话说出来。
- **`const` 成员函数改的可以是"别人"的状态。** `Handle::markDirty()` 是
  `const` 的——它改的是缓存帧里的 `dirty` 位，而帧**不在这个 `Handle` 里**。
  借条自己能改的只有 `pager_` / `pageNo_` / `data_` / `frameIndex_`，
  而"这一页脏了"是**页**的属性，不是借条的属性。
  标成 `const` 之后，`const Handle&` 也能标脏，
  调用方不必为了标个脏就把 `const` 丢掉——**该给 `const` 的地方不给，
  就会逼着别人在别处 `const_cast`**。

### 设计上的坑（比语法坑更值钱）

- **`COUNT(数字列)` 能跑，是撞上的，不是设计出来的。**
  阶段 2 写完时 `COUNT(name)` 会报"只能用在数字列上"——因为 `accumulateValue`
  里 MIN/MAX 有自己的分支先返回了，而 COUNT 没有，于是一路掉到了
  SUM/AVG 的数字类型检查上。`COUNT(数字列)` 恰好不报错，是因为它掉进了
  整数分支**白白加了一通** `intSum`（那个值根本没人看）。
  **"功能看起来能用"和"功能是对的"是两件事**——测一个数字列上的 COUNT
  永远发现不了这个 bug，因为那条路不经过错误分支。
  `aggregate.sql` 里的 `COUNT(name)` 就是为这个补的。
- **前瞻设计和它的回报是可以对账的。** 阶段 1 把 `SelectStmt` 的列
  存成 `vector<ExprPtr>` 而不是 `vector<string>`，当时只是"看着以后要用"。
  阶段 2 加 `score * 2` / `COUNT(*)` 时，**这个字段一个字都没改**，
  改动集中在 parser 里。这就是那层前瞻的全部价值：改动集中在一处，
  而不是散到 ast / parser / executor / printer 四个文件里。
  反过来，如果阶段 1 图省事存了列名，阶段 2 就是四个文件一起动。
- **加一个关键字要付代价。** `ORDER` 变成保留字之后，
  `CREATE TABLE t (order INT)` 就从合法变成了语法错误。
  这个代价在阶段 1 的 README 里就提前记下来了，
  所以阶段 2 加 `ORDER BY` 时没漏——**提前写下"以后这里会破"，
  比事后想起来便宜得多**。
- **"能算的全算一遍"和"存一份"会打架，而且打架的时候不报错。**
  写 `delete_compact.disk` 的时候我算了一遍页里的空间：删掉 20 行、
  压缩之后应该有 1796 字节空，那么一行 1814 字节的应该放得下。
  实测放不下。原因是我假设了"压缩会把槽位数组也缩掉"——
  44 个槽位里 20 个是墓碑，那 80 字节**永远收不回来**。
  真正的原因写在设计决定 20 里（这是个刻意的取舍），但**我的算术
  和代码的算术对不上账的时候，第一反应是"代码有 bug"**。
  教训：写这种断言之前，先把"哪些字节参与计算"照着代码数一遍，
  别照着脑子里的模型数。
- **别手打长串重复字符，用常量算出来。**
  `delete_compact` 里那行 400 个 `D` 我手打成了 416 个，
  而同一文件里两个 `SELECT` 的 `D` 是 694 和 631 个。
  于是查询的 `COUNT(*)` 是 0——**看起来像个存储 bug**，
  查了半天才发现在查一个根本不存在的那串字符。
  后来这些文件改成用常量（`PAD = 74`、`BIG = 400`）生成，
  注释里的数字也从同一批常量里算出来，**这样注释才不会和代码各说各话**。
- **"这一页装不下"必须能表达成返回值，不能表达成异常。**
  `heapInsert` 放不下时返回 `false`，因为"换个页就行"是每天都会发生的事。
  用异常表达一件天天发生的事，异常就不再是异常了——
  真正的异常（数据坏了、页号越界）会被淹在里面。
  同类判断在 `heapCompact` 上：返回"有没有真的收回空间"，
  让调用方能区分"白跑一趟"和"干成了"。
- **删东西的时候，先问"删了之后别人手里的句柄还指得对吗"。**
  槽位数组不能截断、目录记录不能真删、`RowId` 撑大之后可能失效——
  这三个都是同一个问题的三个面。答案是同一个：
  **让失效的东西明确地报失效，比让它悄悄指到别人身上好。**
  阶段 4 加索引之后，这个判断会变成主要矛盾（索引里存的就是 `RowId`，
  而 `UPDATE` 会让它搬家），所以先在 README 里把它写死。
  **这一条在阶段 4 兑现了**：`updateRow` 现在要把新行号返回给调用方，
  索引项按新行号重插——`index_grow_move.disk` 就是它。
- **测试里写死的常量，会在另一边涨价之后悄悄失效。**
  `err_bad_file.disk` 里那个"页大小不对"的构造文件，是把一个字节
  （版本号）写成 `1` 造出来的。阶段 4 把格式版本涨到 2 之后，
  这个文件**先**被版本检查挡住了——那条测试还是绿的，
  但它已经不再测"页大小不对会被拦下来"这件事了，
  测的是"版本 1 会被拦下来"，而版本 1 那个分支同一份文件里已经有一条在测。
  **测试挂掉是好事，测试静悄悄地改测别的东西才是坏事。**
  修法是把那个字节也写成本阶段的版本号，并在旁边注明"这个数要跟着
  `ACORN_FORMAT_VERSION` 走"——**让两个必须一致的东西物理上挨着**。
- **别把测不出来的数字写进注释，先去量。**
  写 `index_big.disk` 的 `!pages` 时我先按"叶子页装满了就对半分"
  手算了一遍页数，算出 19 页，实测 22 页。差的 3 页我没有办法从代码外面
  推出来（分裂点的字节数搜索、内部节点的开销、目录页什么时候分配，
  三件事叠在一起）。所以改成**先跑一次量出来，再拿量出来的数去反推结构**：
  量到 `+5` 页和 `+7` 页，就能反推出"大概是 3 个叶子 + 1 个根"和
  "6 个叶子 + 1 个根"，也就能在注释里说清楚"为什么 400 个 19 字节的项
  会占掉 4 页"。
  **注释里的数字要么是算出来的，要么是量出来的；凭印象写的那一种，
  下一个读的人没有办法反驳它。**

### 阶段 5 撞到的（这一阶段最值钱的三个）

- **★ 从一个只写流里 `fread`，一个字节都读不到，而且不报错。★**
  这是整个项目到目前为止最贵的一个坑。`Journal::openIfNeeded` 里
  建日志文件写的是 `std::fopen(path, "wb")`——`"wb"` 是**只写**。
  而回滚的时候要从这个文件里把旧内容读回来（`forEachRecord`）。
  从一个只写流里读，C 标准说这是**未定义行为**，具体到实现上就是
  **`fread` 返回 0，且 `ferror` 是干净的**。

  症状：回滚把全 0 写回库文件，然后下一次查询报一句
  「不认识的类型标签 255」——**离肇事现场十万八千里**。
  真正的定位办法是先 hexdump 两个库文件比对（一个坏的、一个好的），
  发现坏的那个第 1 页整个是 0；然后在 `record` / `readAt` / 回放
  三个点上各加一句临时 `fprintf`，才看到
  `[DBG record] first8=03 00 00 00 FF FF FF FF`（记进去的是对的）
  但 `[DBG readAt] got=0`（读出来是空的）。

  修法一个字：`"w+b"`（那个 `w` 负责截断——一个事务一份日志，
  上一次的残留不该混进来，所以不能写成 `"r+b"`）。
  **教训不是"记得加 b"，是"读和写要用同一个流的时候，
  打开模式得把两件事都说出来，而错的那一种不会报错"。**

- **不变式要写成一道会抛异常的检查，而不是一句注释。**
  阶段 5 的核心不变式是"改一页之前，它的旧内容必须已经在日志里"。
  写进注释里是不够的——`markDirty()` 真的放了那道检查：
  违反就抛「内部错误：……是被改过的，但它没有先经 getForWrite 记进日志」。
  它在**第一次冒烟测试**（`BEGIN; INSERT; ROLLBACK`）就抓到了
  十几个还在用 `get()` 改页的调用点。
  **要是只写在注释里，这些调用点会活到"回滚之后数据对不上"的那一天。**

- **有些 bug 测不出来，只能靠把顺序写对。**（设计决定 41）
  `allocatePage()` 里那句 `ensureTransaction()` 晚一行，就会
  "每回滚一次建表漏 4KB"，**而且读不出坏数据、不报错、查不出来**。
  这不是"测试没写够"，是这类 bug 的性质：它破坏的是一致性，
  不是任何一次具体的读写。能做的只有把理由写在代码里那句的旁边，
  让下一个想把它挪走的人看见。

### 阶段 6 撞到的

- **★ 同一个问题，报了两个不同的退出码。★**
  这不是编译错误，是**设计错误**，而且它只在"用户按退出码写脚本"这个
  视角下才看得见——人看提示语是看不出问题的（两句话都挺对）。

  "库被占着"在代码里有两条到达用户的路：
  开库时撞上，错误在 `Database` 的构造里抛出来，落在 `main` 的
  "打开失败"那一类，返回 2；库已经开着、敲到 `BEGIN` 升级独占时撞上，
  错误从**语句执行**里冒出来，落在"SQL 的问题"那一类，返回 1。

  发现它的方式是**把退出码也当成测试对象**（`! exit N` 这个指令就是
  为它加的），于是"同一个场景、两个入口"的两条用例摆在一起，
  一个 `! exit 2`、一个 `! exit 1`。**不把退出码钉进测试，
  这个不一致会一直躺在那里，而且躺得很安静。**

  修法见设计决定 48（引入 `BusyError` 类型）。这里记的是那条更泛的教训：
  **一个错误"从哪儿冒出来"不该决定它"是什么错误"。**
  当同一个原因能经由两条代码路径到达用户时，就必须有一个与路径无关的
  表示——在这个项目里是一个类型。

- **★ 库文件是 UTF-8，而 Windows 的 `fopen` 认 GBK。★**（设计决定 49）
  这个是**锁那一层把它带出来的**：锁文件建成功了，库文件建不出来。
  **一个能建、一个不能建**，这个对比就是线索。

  值得单独记的是它的**症状形态**：报的是"目录不存在？没有写权限？"，
  而目录就在那儿、权限也没问题。**报错信息把人的注意力引到了
  一个完全不相干的方向**（去查目录、查权限），
  真正的原因（编码）在提示语里一个字都没提。

  所以教训有两条，第二条比第一条重要：
  1. 跨编码的路径要统一走一层转换；
  2. **当一个错误提示里的"可能原因"全都不成立时，不要继续在那些方向上找，
     要去问"这个判断本身是怎么做出来的"**——`fopen` 返回空不代表
     文件不存在，它代表"我用我理解的那串字节去找，没找到"。

- **`Start-Process -PassThru` 拿到的 `.ExitCode` 在 PowerShell 5.1 上永远是空的。**
  这是**量出来的，不是猜的**：`WaitForExit()` 之后是空的、`Refresh()`
  之后是空的、拿 `Get-Process` 重新取一个对象还是空的。

  它影响的是测试基础设施：`!bg` 起的后台进程，事后没法问它"你退出码是几"。
  一开始 `!wait` 打印的是 `! wait -> it exited with code `（后面空着）——
  **一个尾巴上缺了数字的断言，比没有断言更危险**：它看起来检查了退出码，
  实际上什么也没检查。

  改法的方向是**换一个可靠的观测点**：不测后台进程的退出码，
  改测**前台**进程的退出码（`cmd /c` 会把子进程的状态原样交回来）。
  这本来就是脚本真正看得见的那个东西，测它反而更贴近现实。
  教训：**观测手段不可靠时，换观测点，别在原来的点上打补丁。**

- **读一个还活着的进程写出来的文件，会被"文件正在使用"挡住。**
  后台进程的 stdout 是重定向到文件的，而它还没退出——这时候
  `[System.IO.File]::ReadAllText` 会直接失败。
  原因是默认的共享模式不允许别人在写入方还持有时读它。
  改成自己开一个 `FileStream` 并显式给 `FileShare.ReadWrite` 就好了。

  这一条是 `!bg` 那个"等它就绪"的轮询必须用的：**要判断后台进程
  "开好库、拿好锁了没有"，唯一的办法就是去读它已经打出来的那行字**——
  而那行字所在的文件此刻正被它自己开着。

- **`Stop-Process` 打在一个已经退掉的进程号上会抛异常，然后把整个测试跑掀翻。**
  `run_tests.ps1` 开头是 `$ErrorActionPreference = 'Stop'`，
  所以一句 `Stop-Process -Id 13612` 直接变成一整屏 PowerShell 调用栈，
  后面几十条用例一条都没跑。而且**原因没复现出来**
  （进程号明明刚拿到，中间它自己退了）。

  **没复现出来的 bug 也得修**——因为它的性质是清楚的：
  "我杀它的时候它可能已经死了"本来就是常态，不是意外。
  修法是两件事一起做：先问 `HasExited`，**是就诚实地报一句失败**
  （而不是硬杀），并且 `-ErrorAction SilentlyContinue` 兜住竞态
  （问完到杀之间它还是可能死掉）。

  **这里的取舍很值得说**：进程已经不在时**不该静悄悄地过**。
  `!killbg` 是"我要杀掉一个正在占着库的进程"，如果它早就退了，
  那条用例的前提就不成立了——**测试该红，不该绿**
  （正是上面那条"测试静悄悄地改测别的东西"的同一个道理）。

- **拿一个"睡 500 毫秒它就绪了"的假设去写并发测试，等于写了个随机失败的测试。**
  `!bg` 一开始就是这么设计的，改掉了。两个方向都会错，而且都很难查：

  - **睡太短**：后台还没拿到锁，前台那条"应该被挡住"的命令**成功**了，
    于是断言的是"它没被挡住"——**测试红了，但红的是测试不是代码**。
  - **睡太长**：机器一忙就超时，测试时绿时红。

  改法是**别睡，去问状态**：轮询后台进程已经打出来的那行字
  （它一起手就会打印自己拿到的锁），拿到才算就绪；
  再加一个"它万一直接死了"的出口，把它的输出原样记进 `.out`——
  **不然一个起不来的后台进程，看起来就像一条没跑的用例。**
  睡固定时长这件事，本身就是"我不知道怎么判断它好了没有"的自白。

- **在一个进程里测锁，测的其实是"同一个进程能不能锁两次"。**
  这一阶段最基本的风险是：测试看起来在做并发，实际上一个进程都没并起来。
  操作系统对**同一个进程**的重复加锁往往另有规则（同一句柄上的重入、
  同进程不同句柄的放行……），所以哪怕锁根本没生效，
  这种测试也是绿的。

  所以六条锁用例里有**五条**至少两条进程：`!bg` 起一条占着，
  前台再发命令，靠 `! exit 2` 断言它被挡住了。
  而最能说明问题的是 `lock_released_on_kill.disk`——
  它把后台进程**杀掉**，然后证明下一条命令立刻就能用。
  这一条是"锁归内核所有"这个设计的唯一直接证据，
  而它在单进程测试里**根本无法表达**。

  第六条 `lock_info_state.disk` 是单进程的，而且是**故意**的：
  它看的是锁的**生命周期**（共享 → `BEGIN` 时独占 → `ROLLBACK` 后共享），
  这件事只能在进程内部从 `.info` 上看。但要说清楚的是——
  **它证明不了跨进程互斥**，一个字都证明不了。
  两条用例的分工就写在这里：一条证明"锁跟着事务走"，另一条证明"锁真的挡住了别人"，
  谁也替代不了谁。

## 路线图

- [x] **阶段 1 · 全内存最小可用** —— `CREATE` / `INSERT` / `SELECT ... WHERE`，
      REPL，测试。存储层的接缝（`Table::scan`）已经留好。
- [x] **阶段 2 · SQL 完整一点** —— `UPDATE` / `DELETE` / `ORDER BY` / `LIMIT` /
      `IS NULL` / 聚合函数 / `SELECT` 里的算术 / `AS` 别名。
      `ORDER` 和 `AS` 已变成保留字。
- [x] **阶段 3 · 落到磁盘** —— 4KB 固定页、槽位页、64 格时钟页缓存、
      空闲页链表、目录页、`DROP TABLE`、`-d` 与内存库两种模式。
      `Table` 内部整个换掉了，但 `scan` 的签名没变；
      `RowId` 从 `size_t` 变成了 `(页号, 槽位号)`，执行器一个字没改。
      `DROP` 是保留字了。
      测试多了 `disk\` 这一类——一行一个进程，唯一能证明数据活过进程边界的写法。
- [x] **阶段 4 · 索引** —— 自己写的 B+ 树，叶子页串成链，键是 `(值, 行号)`。
      `CREATE INDEX` / `DROP INDEX`、`WHERE` 上的等值和区间都走索引。
      查询计划器自己判断条件能不能用索引，认不出就退回全表扫。
      删除**不合并、不借位**（复制上来的分隔键让旧分隔键永远安全），
      这是这一步最大的一笔设计取舍。
      `RowId` 被 `UPDATE` 弄失效这件事在这里兑现了：
      行搬家之后索引项跟着换行号。
      `INDEX` 和 `ON` 成了保留字；文件格式版本从 1 涨到 2
      （索引目录链用了原来留的保留字节）。
- [x] **阶段 5 · 事务** —— 自己写的**回滚日志**（`<库文件>-journal`）、
      `BEGIN` / `COMMIT` / `ROLLBACK`、自动提交、崩溃恢复。
      核心不变式是"改一页之前，旧内容必须已经在日志里"，
      它同时管住了"一条语句改一半"和"写到一半断电"两件事。
      阶段 3 欠的那张条子（`UPDATE` 改到一半失败会留下痕迹）在这里兑现。
      **"提交"这个动作就是删掉日志**——日志在不在是唯一的判据。
      `BEGIN` / `COMMIT` / `ROLLBACK` 成了保留字；
      多了 `--crash-at=commit|exit` 这个测试专用开关。
- [x] **阶段 6 · 并发** —— **选了锁，没选 MVCC**（理由见设计决定 44）。
      锁放在一个单独的 0 字节 `<库文件>-lock` 上，用的是**操作系统给的
      文件锁**，所以进程无论怎么死，锁都由内核收走，没有僵尸锁。
      打开库拿共享锁、`BEGIN` 升独占、提交或回滚退回共享。
      升级时**先放共享再抢独占**，抢不到就报错——宁可偶尔失败，不可死锁。
      `--lock-wait=毫秒` 让愿意等的人等，默认不等（静静地卡住最难查）。
      "库被占着"是一个独立的异常类型，两个入口都返回退出码 2。
      顺手修掉一个真 bug：库文件叫中文名的时候根本建不出来
      （路径是 UTF-8，而 Windows 的 `fopen` 认 GBK），修法见设计决定 49。
      测试多了 `!bg` / `!wait` / `!killbg` 三条指令和 `! exit N` 断言——
      并发这件事不在两个进程之间就没法测。
